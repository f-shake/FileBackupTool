# 08 · 测试、部署与待定项

## 1. 测试策略

**决策：写测试。** 因此文件系统访问从第一天就抽象为接口（见 [06](06-后端与API.md#2-测试驱动的架构约束)）。

### 1.1 唯一不能出错的地方

> **还原出来的文件必须和源文件逐字节一致。**

这是备份工具存在的全部理由，所以它是 CI 的**硬门槛**——不通过不得合并。

### 1.2 测试分层

| 层 | 范围 | 运行 |
|---|---|---|
| **单元测试** | 镜像 replay、全量/增量选取、去重判据、路径归一化、筛选规则、冲突策略、级联删除影响计算 | CI |
| **集成测试（小规模）** | 真实临时目录上的**往返一致性**：随机构造文件树 → 备份 → 改动 → 再备份 → 还原指定快照 → **逐字节比对** | CI 硬门槛 |
| **集成测试（边界）** | 空目录、单文件、超长路径、Unicode 文件名、只读文件、被独占锁定的文件、0 字节文件、大于 2GB 的文件 | CI |
| **故障注入** | 备份中途 kill 进程、模拟磁盘写失败、文件在拷贝过程中被删除 | CI（最小集） |
| **压测** | 10 万文件的合成树 | 手动 |

### 1.3 故障注入的必需项

有一项**必须现在就做**：

> **`Aborted` 快照的处理逻辑必须有测试。**

它是"进程被杀"这个场景唯一的防线——启动自愈把 `InProgress` 标记为 `Aborted`、GC 正确忽略半成品引用的 blob、后续备份不受污染。这条路径没有测试就等于没有实现。

其余故障注入（磁盘写失败、拷贝中被删）可以在 v1 之后补。

### 1.4 必须覆盖的具体场景清单

- 往返一致性（多快照、多增量、含删除与改名）
- 内容寻址去重：同一内容在两个不同路径下 → 只有一个 blob
- `Length` 预筛的两条分支都走到（有同长度 blob / 无同长度 blob），且**断言无同长度分支下不产生白写**
- 部分写入防护：文件在静默期窗口内持续变化 → **不得**进入备份
- 局部扫描：范围继承正确、范围外的删除**不被误判**、超过退化阈值时转全量
- 三个监控钩子：watcher 构造失败 / 缓冲区溢出 / 队列满 → 各自触发全量扫描
- 快照级联删除：影响清单与实删范围**一致**
- 软删除的 blob **不被回收**（[02](02-存储与数据模型.md#5-回收站)的核心规则）
- 目录关系校验：四条违规各自被拒
- 长路径：超长路径不被"静默跳过"，而是**计入失败计数**
- 路径大小写归一化：`IMG.JPG` 与 `img.jpg` 在 Windows 上是同一条记录

## 2. 部署

### 2.1 构建

```
# 前端
cd web && npm ci && npm run build
# 产物拷入 src/FileBackupTool.Api/wwwroot/

# 后端
dotnet publish src/FileBackupTool.Api -c Release -o publish/
```

发布参数（自包含 / 单文件 / 裁剪）见 §4。

### 2.2 首次运行

1. 放置 `appsettings.json`，配置 `DataDir`、连接串、`TrustedProxies`。
2. 通过环境变量提供初始账号密码（**不写死在文件里**）。
3. 启动 → 自动执行 EF migrations → 种子创建用户。
4. 浏览器访问 → 登录 → **强制 TOTP 绑定** → 保存恢复码。
5. 配置还原根白名单。

### 2.3 nginx

见 [05](05-认证与安全.md#6-nginx-协同)。

### 2.4 Windows 服务（nssm）

**当前按双击运行设计**，后续用 nssm 服务化。服务化时必须：

- 把 `DataDir` 改为**绝对路径**（如 `%ProgramData%\FileBackupTool`），因为服务的工作目录与双击运行时不同。
- 配置**专用服务账号**（不要 LocalSystem）——这个应用能写文件系统，跑在 LocalSystem 下等于把风险放到最大。若有 UNC 目标，该账号需要相应凭据。
- 设置**自动重启**。

## 3. 验收清单

方案实施完成后，逐条验证：

- [ ] 强制单实例：同时启动两个进程，第二个必须退出并给出明确提示
- [ ] 长路径：源目录含超长路径时，文件被正确备份（或明确计入失败），**不静默跳过**
- [ ] 备份中途 kill 进程 → 重启后快照显示"已中断"，后续备份不受影响
- [ ] 同一个文件在两个路径下 → 备份目录里只有一个 blob
- [ ] 全量备份一个 10GB 未变更文件 → **不产生任何写入**（去重命中）
- [ ] 全量备份一个 10GB 新文件 → 只读一次源文件
- [ ] 含 `$RECYCLE.BIN`、隐藏/系统文件的源 → 正确的包含/排除行为
- [ ] UNC 源 → UI 显示"轮询模式"，且确实定期扫描
- [ ] 备份目标目录在源目录内 → **保存任务时被拒绝**
- [ ] 还原到白名单之外 → 被拒绝
- [ ] 删除一个中间增量 → 对话框列出全部受影响的快照
- [ ] 删除快照后 → blob 移入 `_deleted/`，回收站占用可见，**空间未释放**
- [ ] 清空回收站 → 空间释放
- [ ] 还原 → 文件逐字节一致，且时间戳恢复
- [ ] 还原冲突 → 默认跳过，不静默覆盖
- [ ] 备份时有文件被独占锁定 → 跳过并计入失败，快照显示"成功（N 个失败）"
- [ ] 枚举 10 万文件时内存稳定（不随文件数线性增长）
- [ ] 浏览器断开 SignalR → 自动降级轮询，UI 显示"轮询"
- [ ] nginx 后 → 登录限流按真实客户端 IP 生效（不是全站共用一个配额）
- [ ] 未绑定 TOTP → 无法访问任何业务功能

## 4. 我替你定的默认值（可否决）

以下条目你没有明确表态，我按工程惯例定；**任何一条都可以要求改**。

### 4.1 技术细节

| 项 | 我的默认 | 说明 |
|---|---|---|
| **API 风格** | 控制器风格 REST（非 Minimal API） | 端点数量多，控制器更好组织 |
| **分页响应格式** | `{ items, total, page, pageSize }` | 全局统一 |
| **错误响应格式** | `{ code, message, detail? }` | `code` 用稳定字符串（如 `TASK_DIR_CONFLICT`），前端可据此做本地化 |
| **状态管理** | Pinia | 与 Vue 3 生态天然搭配 |
| **测试框架** | xUnit | .NET 生态默认 |
| **DB 批提交大小** | 2000 条记录 / 批 | 需实测调整 |
| **回收站账本** | 单个 `manifest.json` | 而非分片——回收站条目数量应远小于 blob 池 |
| **日志保留** | 文件 30 天；`BackupLog` 表 180 天；`AuditLog` 表永久 | 审计日志不自动清理 |
| **时钟** | 全部走 `IClock`，存 UTC，显示本地 | |
| **发布方式** | `dotnet publish` 框架依赖（非自包含） | 目标机已装 .NET 10 runtime；自包含可选 |
| **SignalR 降级阈值** | 连续 3 次重连失败即切轮询 | |

### 4.2 需要你确认的语义细节

| 项 | 我的默认 |
|---|---|
| **`VirtualFull` 类型是否允许手动触发** | 允许（旧界面有"虚拟全量备份"按钮） |
| **删除任务时如何处理其快照与 blob** | 任务软删除；快照保留；blob 交由 GC（可能因此被移入回收站）。**不物理删除备份目录** |
| **还原根白名单是否允许覆盖源目录** | 允许（"还原回原处"是合法场景），但仍受白名单约束 |
| **Deep hash 校验的默认行为** | 「完整校验」默认只做引用比对，**重算哈希需显式勾选**（TB 级重算极慢） |
| **一个源目录能否被多个任务备份** | 允许（源目录不设唯一约束，只有备份目录唯一） |
| **失败率阈值** | 10%，可配置 |

## 5. 遗留待定项

以下是设计树里**尚未定论**的点，明确记录而非默认假设：

1. **cron 调度的具体形态**：两种模式都要（已定），但 v1 只做固定间隔。cron 的 UI（表达式输入 + 下次触发预览）留待后续。
2. **深快照链的浏览预物化**：链长超过阈值时是否后台物化镜像以加速浏览。v1 不做，但这是个已知的性能悬崖，需要在实际数据上测量。
3. **备份数据静态加密**：v1 不做（见 [05](05-认证与安全.md#71-为什么不做备份数据静态加密)）。若将来要做，必须用**收敛加密**以保留去重能力。
4. **目录重命名的优化**：v1 不处理（表现为一次大快照）。可行方向是监听目录 `Renamed` 后做路径前缀批量替换。
5. **回收站的空间统计**：需要遍历 `_deleted/` 求和。大回收站下可能较慢，是否需要缓存，视实测而定。
6. **`FzLib` 的 RC 依赖**：是否发布 `3.4.0` 稳定版，或改为本地引用（本地引用会破坏 CI）。
7. **多实例/多盘支持**：`GlobalConcurrency` 保留为配置项，但目前固定为 1。真要支持多盘并行需要重新设计队列。
8. **前端是否需要 UnoCSS**：GalleryCloud 用了 UnoCSS + Element Plus。沿用可保持你两个项目的一致，不沿用则少一层依赖。**待你决定。**
