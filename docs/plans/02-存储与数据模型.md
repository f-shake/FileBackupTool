# 02 · 存储与数据模型

## 1. 数据库

**集中式 SQLite**（`App_Data/filebackuptool.db`），EF Core + migrations。

不使用"每任务一个 `db.sqlite`"的旧方案。理由：单一迁移点、能建全局索引、能跨任务查询、无需为每个任务维护连接、元数据可单独备份。

代价：备份目录不再自包含。**由"抢救清单"补偿**（见 §4）。

### 1.1 通用约定

- **所有记录删除一律软删除**（`IsDeleted`）。见 §5 关于回收站的配套规则。
- **所有时间戳存 UTC**。
- 表名与列名使用 EF 默认（PascalCase），不使用复数化。

## 2. 实体模型

### 2.1 `BackupTask` — 备份任务定义

| 列 | 类型 | 说明 |
|---|---|---|
| `Id` | `Guid` | 主键 |
| `Name` | `string(200)` | 任务名 |
| `SourceDir` | `string(1024)` | 需要备份的目录（绝对路径） |
| `BackupDir` | `string(1024)` | 备份文件存放目录（绝对路径） |
| `FilterJson` | `string` | 序列化的筛选规则（`FileFilterRule` 语法） |
| `ByTimeInterval` | `bool` | 是否启用定时备份 |
| `TimeIntervalMinutes` | `int` | 备份间隔（**分钟**，非"时刻"） |
| `MaxAutoIncrementBackupCount` | `int` | 增量链长度上限，超过则跑全量 |
| `IsDefaultVirtualBackup` | `bool` | 自动全量时使用虚拟全量 |
| `ByWatching` | `bool` | 是否启用变更监控 |
| `IsEnabled` | `bool` | **任务级启用开关**（旧设计缺失，见 [07](07-前端设计.md)） |
| `CreatedAt` / `UpdatedAt` | `DateTime` | UTC |

**唯一约束与校验**（保存时强制执行，见 §6）：

- `BackupDir` 全局唯一（禁止共享备份目录）。
- 任意两个任务的 `SourceDir` / `BackupDir` 之间不得存在包含关系。
- `BackupDir` 不得位于自身 `SourceDir` 之内。

### 2.2 `BackupSnapshot` — 快照

| 列 | 类型 | 说明 |
|---|---|---|
| `Id` | `int` | 主键 |
| `TaskId` | `Guid` | FK |
| `Type` | `enum` | `Full` / `VirtualFull` / `Increment` |
| `Status` | `enum` | `InProgress` / `Completed` / `Aborted` |
| `BeginTime` / `EndTime` | `DateTime` | UTC |
| `CreatedFileCount` | `int` | |
| `ModifiedFileCount` | `int` | |
| `DeletedFileCount` | `int` | |
| `FailedFileCount` | `int` | **新增**：本次备份中处理失败的文件数 |
| `TotalBytes` | `long` | **新增**：本次实际写入 blob 的字节数（用于快照列表的"占用空间"列） |
| `AbortReason` | `string` | `InProgress` / `Aborted` 时的手动或自动原因 |

**`Status` 取代旧的 `EndTime == default(DateTime)` 隐式哨兵。** 理由：分批提交必然导致"跑到一半崩溃"留下半截记录；用显式状态后，UI 可以直接显示"上次备份被中断"，GC 有明确依据，也不必再依赖脆弱的时间戳约定。

**查询一律只看 `Status == Completed`。**

**启动自愈**：进程启动时扫描 `Status == InProgress` 的快照，全部标记为 `Aborted` 并写入原因（"进程在备份过程中退出"）。

### 2.3 `BackupFile` — 文件记录（一个路径的一个版本）

| 列 | 类型 | 说明 |
|---|---|---|
| `Id` | `long` | 主键（百万级用 64 位） |
| `SnapshotId` | `int` | FK |
| `TaskId` | `Guid` | 冗余，用于避免 join |
| `RelativePath` | `string(2048)` | 相对源目录的路径（**大小写按平台归一化**，见 §3.3） |
| `Type` | `enum` | `Created` / `Modified` / `Deleted` |
| `Length` | `long` | 文件大小 |
| `ContentHash` | `string(64)` | SHA-256 十六进制；`Deleted` 与虚拟全量为 `null` |
| `FileTimeUtc` | `DateTime` | 源文件的 `LastWriteTimeUtc` |
| `IsDeleted` | `bool` | 软删除 |

**注意**：内容寻址后，旧的 `BackupFileName`（GUID）与 `Hash`（SHA-1）两列**合并为一列** `ContentHash`——blob 名就是哈希。

记录认证与会话事件：登录成功/失败、TOTP 校验、会话创建/踢出、密码修改、任务配置变更、快照删除、还原执行。

| 列 | 说明 |
|---|---|
| `Id` / `Time` / `EventType` / `Actor` / `SourceIp` / `UserAgent` / `Target` / `Detail` | |

### 2.6 `JobQueueItem` — 作业队列（持久化可选）

用于在 UI 上展示"排队中"的作业。**不跨重启恢复**（重启即作废）。

## 3. 索引

索引是这个量级（十万～百万文件）下**性能的生死线**。旧设计一个索引都没有。

| 表 | 索引 | 用途 |
|---|---|---|
| `BackupFile` | `(TaskId, RelativePath, SnapshotId)` | 路径前缀查询（镜像浏览、文件历史） |
| `BackupFile` | `(SnapshotId)` | 按快照取记录 |
| `BackupFile` | `(TaskId, ContentHash)` | blob 引用计数（GC） |
| `BackupFile` | `(TaskId, Length)` | **`Length` 预筛**（见 [03](03-备份引擎.md#33-去重与哈希)） |
| `BackupSnapshot` | `(TaskId, Status, BeginTime)` | 快照列表与链查找 |
| `BackupLog` | `(TaskId, Time)` / `(SnapshotId)` | 日志查询 |
| `AuditLog` | `(Time)` | 审计查询 |

### 3.1 关于镜像重建的查询

浏览某个快照 / 目录的镜像时，**不把整条链 replay 进内存**。做法：

1. 由目标快照向前找到最近一次 `Full`/`VirtualFull`，得到这条链上的快照 id 集合。
2. 一条 SQL 取回**该路径前缀**在链上所有快照中的记录：
   `WHERE TaskId=? AND SnapshotId IN (…) AND RelativePath LIKE 'prefix%'`
3. **只对这一个小集合在内存里 replay**（按 `Snapshot.BeginTime` 排序，依次应用 `Created`/`Modified`/`Deleted`）。
4. 服务端分页返回。

一个目录下涉及的记录通常是几百到几万条（不是百万），replay 成本可控。

**深链优化**：链长超过阈值时，可后台预物化。v1 不做。

### 3.2 大小写归一化

Windows 上 `IMG.JPG` 与 `img.jpg` 是同一个文件。旧的去重逻辑只在**防抖字典的 key** 上做了大小写归一化，而**存进数据库的路径没有归一化**——会产生重复行。

新设计：**平台相关的路径归一化必须在写入与查询两侧统一应用**（Windows 上 `ToLowerInvariant()`，Linux 上保持不变），封装在路径工具类里，不允许任何地方绕过。

## 4. 备份目录磁盘布局

```
<BackupDir>\
├─ blobs\
│  └─ ab\
│     └─ cd\
│        └─ abcdef01…（64 位 SHA-256 十六进制，裸文件，无扩展名）
├─ _deleted\                        # 回收站，见 §5
│  ├─ blobs\ab\cd\abcdef01…
│  └─ manifest.json                 # 回收账本
└─ .manifest\                       # 抢救清单，见 §6
   ├─ <一级子目录名>.json
   └─ …
```

### 4.1 为什么是内容寻址

- **去重从"查库"降级为"文件系统探测"**：blob 是否已存在 = `File.Exists(blobPath)`，省掉旧设计里每次新文件的 `GetSameFile` 全表扫描。
- **文件名校验完整性**：文件名就是内容的哈希，重算一遍即可验证。
- **天然分片**：两级哈希前缀目录，避免单目录堆积百万文件。
- **跨路径、跨时间的真内容去重**：旧设计因为把时间戳放进去重键，实际做不到这一点。

### 4.2 刻意不做的

- **不带原始扩展名**——裸文件不带扩展名是**优点**：防止被备份软件、杀软、索引器二次处理。还原时从 `RelativePath` 重建扩展名。
- **不压缩**——备份对象多为已压缩媒体，压缩只烧 CPU，且让内容无法增量读取。
- **不做目录树/硬链接快照**（用户明确否决）——路径长度问题；且硬链接会引入 NTFS 每文件 1024 链接上限、就地写污染全部快照、空间统计复杂化等结构性风险。

## 5. 回收站

**软删除的记录是元数据层面的。blob 是物理数据，采用"移入回收站"而非物理删除。**

### 5.1 规则

- blob 被判定为垃圾时，**`File.Move`** 到 `<BackupDir>\_deleted\blobs\<同样分片路径>\<hash>`。
  - **目录结构保持不变**，因此每个 blob 在回收站里仍可被唯一定位与恢复。
  - 同卷移动是**元数据操作**，几乎零成本。若跨卷则退化为整文件复制——因此**回收站必须在备份目录内，且与 blob 池同卷**。
- **持续软删除语义**：软删除的记录**仍算有效引用**，blob **不会**被移入回收站。只有"**没有任何记录（含软删除的记录）引用**"的 blob 才会被回收。
  - 这修正了旧设计的一个矛盾：旧代码的 GC 过滤 `IsDeleted == false`，导致软删除的快照其 blob 会被物理删除——**"软删除"名不副实，且比没有更危险**（用户以为能救回来，其实不能）。
- **空间不会自动释放**。UI 必须显式展示"回收站占用 X GB"，用户手动清理 `<BackupDir>\_deleted\` 才释放。
- **回收站被排除在所有扫描之外**：不进 `.manifest`、不被 GC 二次处理、不被备份（由 §7 的目录关系校验保证）。

### 5.2 回收账本

`<BackupDir>\_deleted\manifest.json` 记录每个被回收 blob 的：

```jsonc
{
  "movedAt": "2026-09-22T03:14:07Z",
  "blobs": [
    { "hash": "abcdef01…", "movedAt": "…", "lastPath": "docs/报告.docx", "length": 12345 }
  ]
}
```

理由：移入回收站后，用户在文件系统里只看到 `ab/cd/<64位哈希>`，**完全无从判断这是什么、什么时候删的、能不能删**。没有账本，"待用户手动删除"就变成"待用户盲删"。这些信息在软删除的记录里都是现成的，几乎零成本。

### 5.3 明确不做：从回收站"复活"

当同样的内容需要重新备份时，**不去回收站查找并挪回**，而是从源文件重新拷一份新 blob。

理由：复活会让回收站变成"**第二个 blob 池**"——它的空间统计、GC 语义、以及"待删除"的定位全部混乱。宁可多写一份数据。

### 5.4 触发时机

- **每次备份结束后做一次增量回收**：只检查本次涉及的哈希（该快照写过的，以及该快照标记删除的）。
- **手动的"完整校验 + 回收"入口**：全量交叉比对 blob 池与数据库记录，同时报告"多余文件"与"丢失文件"（丢失 = 有记录但 blob 不在池中也不在回收站中）。

## 6. 抢救清单

**目标：不需要本软件，使用者就能据此分析出应当如何还原。**

因此格式必须是**纯文本、人可读、任何工具可解析**。排除 SQLite 导出（需要工具、有版本兼容问题）。

### 6.1 内容

只含**当前镜像**（不含历史版本）：

```jsonc
{
  "tool": "FileBackupTool",
  "manifestVersion": 1,
  "generatedAt": "2026-09-22T03:14:07Z",
  "taskId": "…",
  "taskName": "文档备份",
  "sourceDir": "D:\\Documents",
  "backupDir": "E:\\Backup\\Documents",
  "blobLayout": "blobs/<hash[0:2]>/<hash[2:4]>/<hash>",
  "fileCount": 12345,
  "totalBytes": 9876543210,
  "latestSnapshotId": 42,
  "latestSnapshotTime": "2026-09-22T03:00:00Z",
  "files": [
    { "path": "报告/2026年度.docx", "hash": "abcdef01…", "size": 12345, "mtime": "2026-09-01T08:00:00Z" }
  ]
}
```

**还原方法**：对每个条目，把 `blobs/<hash[0:2]>/<hash[2:4]>/<hash>` 复制到 `path` 指定的位置。

### 6.2 落盘方式

- **分片**：`<BackupDir>\.manifest\<一级子目录名>.json`。每次备份结束**只重写受影响的片**（含被删除条目的片）。
- **单一子目录内条目过多时**，按二级子目录再分一层。
- **文件总数低于阈值时退回单文件** `<BackupDir>\.manifest.json`（分片在几千文件以下是纯负担）。阈值默认 `10000`，可配置。

### 6.3 不压缩

明文 JSON。压缩会失去"用记事本打开就能读"这一唯一的抢救属性。

## 7. 目录关系校验

保存任务配置时**强制执行**（旧代码的 `ConfigBase.CheckDir` 只在"目录不存在"时报错，这些关系一条都不查）：

1. `SourceDir` 不得等于 `BackupDir`。
2. **`BackupDir` 不得位于 `SourceDir` 之内。**
3. **`SourceDir` 不得位于 `BackupDir` 之内。**
4. 两个任务的 `BackupDir` 不得相同，且不得互相包含。
5. 还原根目录不得位于任何备份目录之内。

第 2 条是最容易犯、后果最严重的配置错误——**它会与实时监控叠加成自我触发的死循环**：备份写入的文件立刻被 watcher 当成新变更，触发下一次备份，无限嵌套。

每条违规都要给出明确的错误信息（指出是哪两个路径冲突、冲突类型是什么），而不是笼统的"配置错误"。

## 8. 数据目录

```
App_Data\
├─ filebackuptool.db           # 集中式 SQLite
├─ filebackuptool.db-wal       # SQLite WAL（必须被所有监控排除）
├─ keys\                       # Identity 数据保护密钥
└─ logs\
   └─ log20260922.txt
```

**注意**：SQLite 的 `-wal` / `-shm` 边车文件会产生高频写入。如果数据目录恰好落在某个源目录范围内，监控会收到海量噪声事件。由 §7 的校验 + 监控侧的扩展名/路径预过滤共同防御。
