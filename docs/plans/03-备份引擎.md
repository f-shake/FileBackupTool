# 03 · 备份引擎

## 1. 快照模型

三种快照类型全部保留：

| 类型 | 记录内容 | blob | 可恢复 |
|---|---|---|---|
| `Full` | 每个文件一条 `Created` 记录 | 写入（已存在的复用） | ✅ |
| `VirtualFull` | 每个文件一条 `Created` 记录 | **不写**（`ContentHash` 为 `null`） | ❌ **不可恢复** |
| `Increment` | 只记录 `Created` / `Modified` / `Deleted` 差异 | 写入 | ✅ |

**`VirtualFull` 的语义**：类似全量备份，但仅将元数据写入数据库，不进行真正的文件复制。用于"我只想看这个目录的变更历史，不需要能还原"。

**必须在 UI 上显著标注不可恢复**——旧设计只在个别 ViewModel 里提示，很容易踩坑。

> 内容寻址让 `VirtualFull` 实现更自然：不写 blob 就是什么都不做。

## 2. 全量 / 增量选取策略

沿用旧语义，**不改**：

```
若 不存在任何 Full/VirtualFull 快照
    → 跑 Full（或 VirtualFull，若 task.IsDefaultVirtualBackup）
否则
    设 full = 最近一次 Full/VirtualFull
    设 n = full 之后（BeginTime 更大）的快照总数
    若 n > task.MaxAutoIncrementBackupCount
        → 跑 Full（或 VirtualFull）
    否则
        → 跑 Increment
```

这是一个**保证增量链不会过长**的模型，与 cron 的"在特定时刻跑"正交。

**实时触发不改变这个逻辑**——它只是把"该跑增量了"这件事**提前**。否则实时备份会退化成"永远增量、永不 full"。

## 3. 备份执行流程

```
BeginBackup
  ├─ 创建 Snapshot { Status = InProgress, BeginTime = UtcNow }
  └─ 提交（以便取得 SnapshotId）
  
枚举源文件（惰性，不物化）
  ├─ DirectoryInfo.EnumerateFiles with EnumerationOptions
  │    RecurseSubdirectories = true
  │    IgnoreInaccessible   = true
  │    AttributesToSkip     = 0        ← 隐藏/系统文件也要备份（.NET 默认会跳过）
  ├─ 应用筛选规则（FzLib FileFilterRule 语法）
  ├─ 硬编码跳过路径含 "$RECYCLE.BIN" 的项
  └─ 跳过备份目录自身（防御性，见 [02](02-存储与数据模型.md#7-目录关系校验)）

处理
  ├─ Increment → 增量路径（§3.2）
  └─ 其他      → 全量路径（§3.1）
  
提交
  ├─ Snapshot.EndTime = UtcNow
  ├─ Snapshot.Status  = Completed（或 Completed with failures）
  └─ 一条集合 UPDATE 把本次所有文件记录翻成 Committed
```

### 3.1 全量路径

对每个枚举到的文件：

1. 计算 `RelativePath`、`Length`、`FileTimeUtc`。
2. 若非虚拟全量 → 走 §3.3 的去重与哈希流程，得到 `ContentHash`。
3. 写入一条 `Created` 记录。
4. `CreatedFileCount++`。

**注意**：全量快照里所有记录都是 `Created`，包括覆盖了之前已备份的文件。

### 3.2 增量路径

1. 取"上一个镜像"的路径集合（见 §4）。
2. 对每个枚举到的文件：
   - 若路径存在于上一个镜像：
     - 若 `FileTimeUtc` 或 `Length` 与镜像中的记录**不同** → 写入 `Modified` 记录；`ModifiedFileCount++`
     - 否则 → 跳过（文件未变）
   - 否则 → 写入 `Created` 记录；`CreatedFileCount++`
3. 上一个镜像中**剩余未被匹配**的路径 → 写入 `Deleted` 墓碑记录；`DeletedFileCount++`。
4. 若快照为空 → 记一条"没有文件改变"的日志。

**变更检测用的是 `(FileTimeUtc, Length)`，不重算哈希。** 这是有意的性能取舍，代价是"同秒、同长度的修改"会被漏掉（经典的时间戳检测盲区）。

### 3.3 去重与哈希

这是引擎里最需要权衡的一段。

**背景**：内容寻址要求"必须先知道内容的哈希，才能知道 blob 该叫什么名字"——所以**算哈希是结构性的、无法绕过**。

**旧的流程**是：读源文件一遍算哈希 → 查重 → 没有再读一遍拷贝。浪费在于**新文件被读了两遍**。

**"边拷边算"**看起来能省掉一次读，但它是个陷阱：拷完才知道内容已存在，则**白写一整份文件**（10GB 的文件就是白写 10GB）。命中率越高越亏，而全量备份里绝大多数文件是没变过的——**命中率恰恰很高**。

**正确的方案：`Length` 预筛。**

> **内容相同的文件，长度必然相同。** 所以在算哈希之前，先按 `Length` 查一次索引——

```
查：是否存在 ContentHash 非空、且 Length == file.Length 的记录？

  否  → 内容必然全新（重复要求内容相同，内容相同要求长度相同）
        → 直接走「边拷边算」：一次读 + 一次写，省掉预读

  是  → 无法证明唯一，老老实实先算哈希（读 1）
        → File.Exists(blobPath)?
             存在   → 复用，0 次写         ✅ 不白写
             不存在 → 拷贝（读 2）
```

**这个判据可证明安全**——绝不会错误去重。且它恰好在最在意的地方生效：**大文件的长度几乎不可能撞车**，所以 10GB 文件走的是一次读 + 一次写；而长度容易撞车的小文件，本来读两遍也不贵。

`Length` 索引是必须的（见 [02](02-存储与数据模型.md#3-索引)）。

### 3.4 哈希算法

**SHA-256**，十六进制小写，64 字符。

- 相对旧的 SHA-1：在公网 + 高安全等级的语境下，保留 SHA-1 会是个被人挑刺的点（尽管这里只用于去重、不用于安全）。
- SHA-256 有 SHA-NI 硬件指令，现代 CPU 单核 1–2 GB/s。**哈希通常不是瓶颈，磁盘才是。**

### 3.5 `WriteThrough` 必须去掉

`FzLib.FileCopyHelper` 使用 `FileOptions.Asynchronous | SequentialScan` 读 + **`WriteThrough`** 写。

`WriteThrough` 绕过操作系统写缓存，每次写都要等底层介质确认才返回，**正好废掉写回缓存本来能做的批量合并与重排**——与机械盘是**最不利的组合**。

去掉它，改用普通异步写。理由：备份是**可重跑**的，最坏情况是某个 blob 写了一半，而**内容寻址天然能发现**（文件名就是哈希，重算即可验证），下次备份重写即可。用"可检测、可重做"换吞吐是划算的。

> 若将来采用"快照即目录树 + 硬链接"方案，此结论需要重新评估——那种方案的校验能力弱。

## 4. 镜像重建

**当前状态 = 最近一次 Full/VirtualFull + 其后所有 Increment 按 `BeginTime` 顺序依次重放。**

- `Created` → 加入
- `Modified` → 替换
- `Deleted` → 移除

**关键改动：全程不把整条链物化进内存。**

旧设计的 `GetLatestFilesAsync` 会把整条链 replay 成一个 `Dictionary<path, entity>`，而增量备份**每次**都要这么做一次——百万文件直接 OOM。

新设计分两种场景：

| 场景 | 做法 |
|---|---|
| **增量备份的变更比对** | **不重建全镜像**。改为数据库端分批 JOIN：把枚举到的路径分批（如每批 5000 个）与"上个镜像"做匹配，每批处理完即释放。见 §5 的局部扫描进一步缩小范围。 |
| **浏览某快照/目录** | 按 [02](02-存储与数据模型.md#31-关于镜像重建的查询) 的"路径前缀 + 单条 SQL + 小集合 replay + 服务端分页"。 |

**旧设计用 `Debug.Assert(false)` 当链路损坏的唯一守卫**（Release 下被编译掉，损坏静默通过）。新设计：

- 重放遇到异常（`Created` 遇到已存在的路径、`Modified`/`Deleted` 遇到不存在的路径）→ 记 `Warning` 日志 + **计入该快照的健康状态**，在 UI 上可查。
- 不静默。

## 5. 实时监控：两套机制

参考 GalleryCloud 的实现，但**必须补上它明确缺失的东西**。

### 5.1 协作契约（GalleryCloud 完全没有）

> **快速路径（watch）只负责产生"该根变脏了"的信号，不承载任何正确性。**
> **权威路径（scan）是唯一能得出"文件已删除"、也是唯一能修复快速路径静默失效的机制。**

GalleryCloud 的两套机制**互不知情**：没有协调代码、没有共享锁、没有互相通知。唯一保证一致性的是一个过滤唯一索引。在相册场景里这可以接受（最坏是等第二天凌晨全量扫描）；**在备份场景里不可接受**——一次漏掉的变更就是永久少一个版本。

**因此必须显式实现三个钩子**（GalleryCloud 三个都缺）：

| 钩子 | 触发条件 | 动作 |
|---|---|---|
| ① 监控器失效 | `FileSystemWatcher` 构造失败，或 `Error` 事件（缓冲区溢出） | **立即对该根排一次全量扫描** |
| ② 队列反压 | 事件队列满 | 使用 `WriteAsync`（**反压**）而非丢弃返回值的 `TryWrite`；同时计数，超阈值则排一次全量扫描 |
| ③ 启动自检 | 进程启动 | **无条件先跑一次全量扫描**，不信任监控器 |

GalleryCloud 的具体缺陷（供对照）：`watcher.Error` **只记一条日志**；`TryWrite` 的返回值**被丢弃**（队列满静默丢事件）；UNC/不支持的文件系统下 `WatchRoot` 把异常 catch 掉，**等于完全没在监控**。还有一次著名事故：`InitializeAsync()` 在 `Program.cs` 里没被调用，**监控整个没启动而没人发现**。

### 5.2 部分写入防护（**备份场景的硬要求**）

GalleryCloud 的 5 秒防抖是"**从第一个事件起的固定窗口**"，**不是静默期**。大文件拷到一半就会被读，解析失败后那一行**根本不会被创建，且不重试**。

在相册里最多少一行记录；**在备份里严重得多**：一份**截断的内容**会被固化成 blob 并算出哈希——而 dedup 键把它当作合法内容，**之后会被反复复用，污染所有后续快照**。

**规则**：

1. 变更进入**待定表**（不是直接触发备份）。
2. 只有当 `(Length, LastWriteTimeUtc)` 在 **`SettleWindowSeconds`**（默认 10 秒，可配）内**不再变化**，才放行到"待备份"。
3. 若在窗口内又变了 → **重置计时**。
4. **对 `IOException` 做有限重试**（3 次指数退避），覆盖"文件被独占锁定"这类静默期检测不出来的情况。

**额外收益**：编辑一个文档保存 10 次，会被折叠成一次生效。

### 5.3 触发语义

**变更 → 标记脏 → 静默期（默认 45 秒无新变更）→ 合并跑一次增量备份。**

一次增量备份要开事务、扫源目录、写日志；单文件高频触发会把 IO 打满并产生大量微小快照。用较长的静默期 + 合并，把海量碎事件折叠成一次备份。

**关键约束**：实时触发只是**提前**跑，**不改变** §2 的全量/增量选取逻辑。

### 5.4 局部扫描

**只重扫发生变化的目录，未变化的目录从上一次镜像直接继承。**

这改变的是**扫描范围**，不是**备份粒度**——一个快照仍然覆盖整个源，只是未变化的部分不重新枚举、直接沿用。

三个必须配套的约束：

1. **周期性全量扫描兜底**：默认**每 6 小时**无条件跑一次全量扫描。局部扫描**发现不了监控器漏掉的事件**——这是它固有的、不可修复的盲区。另外钩子 ① ② 也会触发即时全量。
2. **退化阈值**：若本次涉及的脏目录数占比超过 `LocalScanDegradeRatio`（默认 30%），直接退化为全量扫描——此时局部扫描的开销已接近全量。
3. **删除检测的范围**：只在该目录子树内做"磁盘上没有 → 标记删除"，子树外一律不动。

一次备份覆盖多个脏目录时，它们被**合并为同一个快照**。

### 5.5 本地盘 vs 网络路径

| 源类型 | 机制 |
|---|---|
| **本地盘** | `FileSystemWatcher`（快速路径）+ 扫描（权威路径） |
| **UNC / NAS / 映射盘** | **放弃 watcher**，只跑轮询扫描（默认每 3 分钟一次）。**UI 上显式标注"此源使用轮询模式"** |

理由：`FileSystemWatcher` 在 UNC/网络路径上**会静默失效**（GalleryCloud 就是这么被坑的：`WatchRoot` 把异常 catch 掉，等于完全没在监控，唯一兜底是等第二天凌晨）。

轮询间隔比 GalleryCloud 那个 24 小时的兜底激进得多，因为备份没有"第二天再说"这种廉价容错。

### 5.6 监控器的实现要点（值得抄的部分）

GalleryCloud 的并发形状是好的，照抄：

- **watcher 回调里不做任何 IO**——只做路径扩展名预过滤与入队。
- **有界 Channel** 汇聚所有监控器的事件。
- **单消费者**，逐批处理。
- **每个合并窗口一个 `DbContext` scope，一次 `SaveChanges`**。

**必须修正的**：

- `TryWrite` → `WriteAsync`（反压）。
- 防抖字典的 key 必须在**平台相关的大小写归一化之后**构造，且**写入数据库的路径也要归一化**（GalleryCloud 只做了前者）。
- 扩展名/路径预过滤必须排除**自己的数据目录**（SQLite 的 `-wal` / `-shm` 边车文件会产生高频噪声）。

### 5.7 目录重命名：不特殊处理

**明确放弃**处理目录重命名。

代价：目录一改名，那棵子树会表现为"旧路径全删 + 新路径全增"，产生一个**和该子树等大的快照**。

好消息：内容寻址让它**不会重新拷贝数据**（内容相同 → 哈希相同 → blob 已存在）。
坏消息：**仍然要把整棵子树重读一遍算哈希**。所以代价是"读一遍"，不是"写一遍"。

> 若将来想优化，可行方向是监听目录 `Renamed` 事件后对子树做路径前缀批量替换。但这依赖目录事件可靠，且需要周期性全量扫描兜底漏掉的场景。v1 不做。

## 6. 调度

### 6.1 两种模式都要，v1 只实现固定间隔

| 模式 | 语义 | v1 |
|---|---|---|
| **固定间隔** | 每 N 分钟检查一次，到期则按 §2 决定全量/增量 | ✅ |
| **cron 表达式** | 在指定时刻触发（如 `0 3 * * 1` = 每周一凌晨 3 点） | ❌ 后续 |

**两者都要**（表达力互补），但 v1 先做固定间隔——它才是备份的正确模型（保证增量链不会过长），cron 保证的是"在特定时刻跑"，两者正交。

> 旧实现把"备份时间间隔"做成了一个 **TimePicker（选时刻）**，语义是错的。新设计改为**分钟数的数值输入**。

### 6.2 检查节拍

后台服务每 60 秒检查一次所有任务：

- `IsEnabled` 且 `ByTimeInterval` 且 `Status` 不是 `InProgress`
- 且 `LastBackupTime + TimeInterval <= now`
- → 入全局作业队列

**注意**：旧设计用 `IsBackingUp` 这个**进程内字段**判断"是否正在备份"，在 Web 宿主下不可靠。新设计以**数据库中的快照状态**为准。

## 7. 错误处理

### 7.1 逐文件失败

| 后果 | 处理 |
|---|---|
| 单个文件读取/拷贝失败（`IOException`、`UnauthorizedAccessException`、`PathTooLongException` 等） | **跳过并记录**，`FailedFileCount++`，继续处理下一个文件 |
| 失败率超过阈值（默认 **10%**）或连续失败 100 次 | **中止整个备份**，快照标记 `Aborted` |

**旧设计的 bug**：只 catch `IOException`。`UnauthorizedAccessException` **不是 `IOException` 的子类**，遇到一个无权限的文件会让**整个备份直接炸掉**。必须修。

### 7.2 快照必须携带失败计数

> **备份工具最危险的失败模式不是报错，而是"显示成功但实际不完整"。**

因此快照完成后，UI 必须明确显示"完成，但 N 个文件未能备份"，而不是一个绿色的成功图标。

### 7.3 取消

用户主动取消 → 快照标记 `Aborted`，UI 立即提示"本次备份已作废"。
（旧设计只留一句"备份被中止"的日志，且 `succeed` 保持 false——可接受但不明确。）

**取消/崩溃后遗留的 blob**：不立即删除。它们可能被其他快照（或软删除的记录）引用。交给 §8 的 GC 处理。

### 7.4 崩溃

进程被杀 → 快照停留在 `InProgress`。启动时自愈扫描把它标记为 `Aborted`（见 [02](02-存储与数据模型.md#22-backupsnapshot--快照)）。

## 8. Blob 回收（GC）

| 时机 | 范围 |
|---|---|
| **每次备份结束后** | 增量回收：只检查本次涉及的哈希 |
| **手动"完整校验 + 回收"** | 全量交叉比对 blob 池与数据库记录 |

**回收判定**：一个 blob 可回收 ⟺ **没有任何记录（含软删除的记录）引用它**。

**回收动作**：`File.Move` 到 `<BackupDir>\_deleted\`（见 [02](02-存储与数据模型.md#5-回收站)）。

**同时报告两类异常**：

- **多余文件**：blob 池里存在但没有记录引用（正常应被回收）。
- **丢失文件**：有记录引用但 blob 既不在池中也不在回收站中（**会导致还原失败**，必须显著告警）。

> 旧实现的识别方式是"文件名长度 == 32"这种启发式，会误伤用户自有的 32 字符文件名。新实现按**哈希格式**识别，不使用长度启发式。
