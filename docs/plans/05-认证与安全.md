# 05 · 认证与安全

## 1. 威胁模型

**部署前提**：站点**暴露在公网**，nginx 终止 TLS，单用户。

这决定了安全等级必须是"高"，而不是内网工具的那种"够用就行"。

### 1.1 最关键的一条：这个应用能写服务器上的文件

| 能力 | 后果 |
|---|---|
| 列出服务器任意目录（目录浏览 API） | 信息泄露 |
| **还原 = 写文件到服务器** | **任意文件写入 ≈ 服务器沦陷** |
| 备份 = 读任意文件 | 数据外泄（但用户已声明"文件不出服务器"，所以不做下载） |

**一个被攻破的会话就等于服务器沦陷**——攻击者可以往启动目录写文件、可以覆盖任意文件。

因此：

1. **还原目标限制在白名单还原根目录内**（见 [04](04-还原与快照管理.md#13-目标路径白名单)）。这是最重要的缓解，成本极低。
2. **TOTP 强制开启**——单用户系统里，这是防"密码泄露即全崩"的唯一低成本手段。
3. **不要用 LocalSystem 跑服务**（若将来用 nssm 部署）。

## 2. 认证

### 2.1 ASP.NET Core Identity

**用 Identity，不自建。** 理由：公网 + 高安全等级需要的**账户锁定、密码策略、安全戳（改密即失效全部会话）、TOTP 原生支持**，正好是 Identity 内置的；自建等于把它们重写一遍还更容易写错。

单用户系统上 Identity 的"负担"只是多几张表——集中式 SQLite 里毫无压力。

**种子**：启动时若不存在用户，用配置的初始账号创建（初始密码通过环境变量或首次运行向导提供，**不写死在代码里**）。

### 2.2 TOTP 强制

- 首次登录后**强制进入 TOTP 绑定流程**，未绑定前不能访问任何业务功能。
- 提供**恢复码**（一次性、离线保存），防止验证器丢失后彻底锁死。
- 允许在验证通过后重新生成恢复码。

### 2.3 密码策略

沿用 Identity 默认并收紧：最小长度 12、需要大小写数字符号、不允许与用户名相同。

## 3. 会话

| 项 | 决策 |
|---|---|
| 载体 | **Cookie**（不是 JWT） |
| 标记 | `HttpOnly` + `Secure` + `SameSite=Strict` |
| 滑动过期 | 7 天 |
| 绝对过期 | 30 天 |
| 多会话 | **允许**，提供会话列表 + 单独踢出 |
| 改密码 | 靠 Identity 安全戳**一次性失效全部会话** |

**为什么允许多会话**：用户的原始动机里包含"从手机远程查看"，用"新登录踢掉旧会话"会把它堵死。但必须有会话列表和踢出能力，以便发现异常登录。

**Cookie 认证 + 写操作 = CSRF 必须防**：全部写操作启用 antiforgery。`SameSite=Strict` 已经提供了主要防护，但不要只依赖它。

## 4. 限流与防爆破

| 项 | 值 |
|---|---|
| 登录接口限流 | 每 5 分钟 5 次（按 IP） |
| 账户锁定 | 连续 5 次失败锁定 15 分钟 |
| 全局 API 限流 | 按认证状态分别配额 |
| 上传/写入类接口 | 更严格 |

**IP 来源必须是 `X-Forwarded-For`，且只信任 nginx 的 IP。**

否则限流看到的全是 `127.0.0.1`，会退化成"所有人共用一份配额"——既挡不住攻击，又会误伤自己。详见 §6。

## 6. nginx 协同

nginx 终止 TLS，Kestrel 只监听 `localhost`。

### 6.1 必须配置的四项

**① `ForwardedHeaders` 中间件**

```csharp
builder.Services.Configure<ForwardedHeadersOptions>(o =>
{
    o.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    o.KnownProxies.Clear();
    foreach (var ip in trustedProxies) o.KnownProxies.Add(IPAddress.Parse(ip));
});
app.UseForwardedHeaders();   // 必须在 UseAuthentication 之前
```

**② 只信任 nginx 的 IP**

`X-Forwarded-For` **可被客户端伪造**。信任所有来源等于限流形同虚设。`KnownProxies` 只填 nginx 的地址。

**③ `UseHttpsRedirection` 可能死循环**

反代后应用看到的 scheme 是 `http`，若无条件重定向到 https，nginx 再转发回来又会重定向……必须按 `X-Forwarded-Proto` 判断，或干脆关掉重定向、只依赖 HSTS。

**④ HSTS 由应用设置，nginx 侧透传。**

### 6.2 nginx 侧要点

- `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`
- `proxy_set_header X-Forwarded-Proto $scheme;`
- `proxy_set_header Host $host;`
- **SignalR 需要 WebSocket 升级头**：`Upgrade` / `Connection`，且关闭 `proxy_buffering`。
- 客户端最大请求体大小按需设置（本应用没有大文件上传，可设小值）。

## 7. 传输与存储

| 项 | 决策 |
|---|---|
| 传输 | 全程 HTTPS（nginx），HSTS |
| 备份数据静态加密 | **不做**（见下） |
| 数据库 | 明文 SQLite（`App_Data`） |
| 数据保护密钥 | Identity 的 keyring 存 `App_Data/keys`，**必须排除在备份范围外** |
| 配置中的密钥 | 通过环境变量注入，不写进 `appsettings.json` 提交到仓库 |

### 7.1 为什么不做备份数据静态加密

- 加密会**破坏内容寻址的去重能力**（相同内容加密后不同）——除非做收敛加密，那又引入新的复杂度与风险。
- 备份数据"不出服务器"已经由架构保证（没有下载功能）。
- 真正的防线是**访问控制**（白名单还原、强制 TOTP、限流），而不是把 10TB 备份重新加密一遍。

**若将来必须加密**，正确做法是内容寻址 + 收敛加密（按内容派生的密钥），而不是逐文件随机 IV 加密。留作后续议题。

## 8. 其他

| 项 | 决策 |
|---|---|
| 错误页 | 生产环境不泄露堆栈 |
| 目录浏览 API | 必须认证；不提供符号链接穿越；不返回文件内容（只返回名称/类型/时间） |
| 任务配置校验 | 目录关系校验（见 [02](02-存储与数据模型.md#7-目录关系校验)）——这既是正确性问题也是安全问题 |
| 反向代理信任 | 见 §6 |
| CORS | **不需要**（前端由同源后端带起），因此不配置 CORS——不开放比开放更安全 |
