# 04 · 还原与快照管理

## 1. 还原

### 1.1 这是纯新增功能

ArchiveMaster **根本没有还原**。它的"取回数据"路径只有**另存为**（单文件或单文件夹 → 系统文件选择器选目标路径 → 一个复制进度对话框）。没有整快照还原、没有目标根目录概念、没有冲突策略、没有结果汇总、没有还原日志。`RestoreService` 只用来**构建显示用的树**，真正的 IO 长在 `BackupManageCenterViewModel.Files.cs` 里。

所以本设计的还原**没有现成 UX 可抄**，自由度更大；但也意味着"从桌面版迁过来"的用户会期待至少不低于"另存为"的能力——**做不到就是能力倒退**。

### 1.2 粒度

| 粒度 | 说明 |
|---|---|
| **整快照** | 把某个快照的整个镜像还原到目标根 |
| **目录** | 还原镜像中的某个子树 |
| **多选文件** | 勾选任意一组文件还原 |

### 1.3 目标路径：白名单

> **还原到配置的"还原根目录"白名单之内。绝不接受任意路径。**

配置项：`Security.AllowedRestoreRoots: string[]`（绝对路径数组）。

**为什么这是硬约束**：还原是**写文件**操作。这个应用能读服务器上任意路径（目录浏览）并且能写（还原），**一个被攻破的会话就等于服务器沦陷**——攻击者可以往启动目录写文件、可以覆盖任意文件。白名单是低成本、高收益的缓解手段。

校验：目标路径必须落在白名单根的子树内；`..` 与符号链接穿越必须被显式拒绝。

### 1.4 冲突策略

逐文件可选，**全局默认"跳过"**（选最不具破坏性的那个）。

| 策略 | 行为 |
|---|---|
| **跳过**（默认） | 目标已存在则不动 |
| 覆盖 | 覆盖目标 |
| 保留两者 | 目标重命名为 `原名 (1).ext` 之类 |
| 较新者优先 | 比较时间戳决定 |

**不做静默覆盖**——旧设计的"另存为"用的是 `FileMode.Create`，会**静默覆盖**目标文件。这是必须修掉的。

UI 上应提供"应用到全部冲突"的勾选，避免逐文件弹窗。

### 1.5 执行

- 还原**纳入全局 IO 作业队列**（见 [01](01-总体设计.md#41-全局-io-作业队列核心约束)），与备份互斥。
- 排队时 UI 显示"已排队，前面还有 N 个作业"。
- 还原过程显示进度（字节级），可取消。
- **恢复原始时间戳**（`File.SetLastWriteTimeUtc` 设为记录的 `FileTimeUtc`）。
- 目标目录按需创建。
- 完成后给出**结果汇总**：成功 / 跳过 / 失败 各多少，附失败文件清单（旧设计只把错误弹一次，不做聚合）。

### 1.6 不可恢复的情况

| 情况 | 提示文案 |
|---|---|
| 记录来自 `VirtualFull` 快照（`ContentHash` 为 `null`） | 「该文件不存在实际备份文件，可能是由虚拟快照生成」 |
| blob 丢失（既不在池中也不在回收站） | 「该文件不存在实际备份文件，可能是文件丢失」 |

批量还原时，若有部分文件不可恢复 → 先明确列出受影响的文件，让用户选择"是否还原其余文件"，**不要静默跳过**。

### 1.7 从回收站恢复

**v1 不做**。回收站是"待用户手动清理"的目录，不是第二备份源（见 [02](02-存储与数据模型.md#53-明确不做从回收站复活)）。

但回收账本（`_deleted/manifest.json`）记录了每个 blob 移入前的最后路径，**用户可以手动把文件拷回**。这是有意的设计：提供信息，不提供自动化。

## 2. 快照管理

### 2.1 列表与分组

**按全量快照分组**：每个 `Full` / `VirtualFull` 开一个新组，其后所有 `Increment` 归入该组。

UI：一个全量快照选择器（下拉）+ 下方列出该组内所有快照的表格。

| 列 | 说明 |
|---|---|
| 类型 | 全量 / 虚拟全量 / 增量 |
| 新增 / 修改 / 删除 | 文件计数 |
| **失败** | **新增**：本次未成功备份的文件数 |
| **占用空间** | **新增**：本次实际写入 blob 的字节数（旧设计没有这一列） |
| 开始时间 / 完成时间 | UTC 存储，按本地时区显示 |
| 操作 | 删除 |

**补齐项**（见 [07](07-前端设计.md#3-相对旧界面的补齐清单)）：类型/日期筛选、分页。

### 2.2 删除的级联语义

**语义不变**：删除一个快照，会**级联删除**它到下一个 `Full`/`VirtualFull`（不含）之间的所有快照。

**这是硬约束，无法回避**——增量链一旦断裂，其后的增量就无法 replay。

**改进的是交互，不是语义**：

> 删除确认对话框**必须列出受影响的全部快照**（时间、类型、数量），而不是像旧设计那样只说一句「删除此快照，将同步删除后续的增量快照」。

用户点一下删掉后面几十个增量，现在是他根本不知道的。

**物理上不立即释放空间**：删除是软删除；blob 只有在"没有任何记录（含软删除记录）引用"时才移入回收站。所以删快照后，回收站占用会增长，UI 需要展示。

### 2.3 保留策略

**默认全手动。**

外加一个**可选的定时自动淘汰开关**：

- 关闭时：快照只能手动删除。
- 开启时：按用户设定的规则（按数量 / 按天数 / 按占用空间）自动淘汰最旧的快照链组。
- **开启时必须二次确认**，并明确告知"这会永久删除备份历史"。

理由：自动删除用户的备份历史是**不可逆的惊喜**，不该是默认行为。但需求真实存在，所以提供一个显式开关。

### 2.4 完整性校验

提供手动入口「完整校验」，执行：

1. 交叉比对 blob 池与数据库记录，报告**多余文件**与**丢失文件**。
2. 校验每个快照链的连续性（是否存在断裂）。
3. 可选：抽样重算哈希验证 blob 完整性。

旧实现里有一个独立的"整理文件"按钮做第 1 项，且识别方式是不可靠的"文件名长度 == 32"启发式。新实现按哈希格式识别。
