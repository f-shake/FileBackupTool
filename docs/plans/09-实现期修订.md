# 09 · 实现期修订记录

`01`–`08` 是 2026-09-22 冻结的设计契约。本文记录**实现过程中对它的偏离**，逐条给出理由。

分类：

- **【必要】** —— 不改就实现不出文档自己要求的行为
- **【补充】** —— 文档没规定，我按工程判断加了，可以否决
- **【修正】** —— 文档的说法在实现中被证明有问题

## A. 数据模型

### A1【必要】`BackupFile.RelativePathKey` —— 归一化必须与显示路径分开存

文档 [02 §3.2](02-存储与数据模型.md#32-大小写归一化) 要求"平台相关的路径归一化必须在写入与查询两侧统一应用"。
但若把归一化后的值**直接存进 `RelativePath`**，原始大小写就永久丢了：

- 增量备份里未变化的文件不写新记录，于是它一直沿用旧记录里那个小写路径；
- 还原时按 `RelativePath` 重建文件名 → **还原出来的文件名会全变小写**。

在 Windows 上"能跑"，在 NAS / Linux 上就是改名。而往返一致性是 CI 硬门槛（[08 §1.1](08-测试与待定项.md)）。

所以拆成两列：

| 列 | 用途 |
|---|---|
| `RelativePath` | **保留原始大小写**，只用于还原时重建路径 |
| `RelativePathKey` | 归一化形式（Windows 上小写），所有比对 / 索引 / 唯一性都走它 |

### A2【必要】路径索引的 `SnapshotId` 建成 DESC

物化"上一个镜像"时按 `(RelativePathKey ASC, SnapshotId DESC)` 扫描（同一路径的记录连续且最新的排在最前）。
索引方向若不一致，SQLite 会为百万行做一次外部排序。见 [02 §3](02-存储与数据模型.md#3-索引)。

### A3【补充】`BackupSnapshot.ImageFileCount` / `ImageTotalBytes`

文档 [02 §2.2](02-存储与数据模型.md#22-backupsnapshot--快照) 没有这两列。但抢救清单的头部
（`fileCount` / `totalBytes`）需要一个**当前镜像**的规模，而按文档的做法只能靠全量 replay 才算得出来——
百万文件下不可接受。

增量维护它们几乎免费（全量时取本次计数，增量时在上个快照基础上加减）。顺带让快照列表多出
"镜像文件数 / 镜像总大小"两列。

### A4【修正】没有建 `JobQueueItem` 表

文档 [02 §2.6](02-存储与数据模型.md) 列了这张表，但同一段自己说"持久化可选"、"不跨重启恢复"。
既然重启即作废，落库只会留下过期行、并且需要一个清理任务。作业队列做成**纯进程内**的
`IJobQueue`（单消费者 Channel）。

### A5【补充】新增 `AppSetting` 键值表

[06 §4.9](06-后端与API.md) 的 `/api/settings` 需要一个**可即时修改**的全局设置存储
（还原根白名单、保留策略）。基础设施配置仍在 `appsettings.json`，只有业务侧设置进库。

## B. 引擎

### B1【修正】快照链的区间比较一律用 `SnapshotId`，不用 `BeginTime`

**这是实现期实测踩到的 bug**，属于"不报错、只静默产生错误结果"那一类：

> 用 `BeginTime > full.BeginTime` 筛选链上的增量时，只要两个快照的 `BeginTime` 相等
> （时钟粒度、或备份快到同一刻），目标快照就会被**静默排除在链外**，
> 表现为"墓碑记录写了，但镜像里那个文件还在"。

正确的不变量是：**同一任务的 `SnapshotId` 递增 == 创建顺序 == 链序**
（`PreviousMirrorTable` 本来就是按这个假设物化镜像的）。所以全部改成按 Id 比较：
[`SnapshotChainPolicy`](../src/FileBackupTool.Core/Snapshots/SnapshotChainPolicy.cs)。

### B2【补充】`JobOptions.FailureRatioMinSamples`（默认 20）

[03 §7.1](03-备份引擎.md) 只说"失败率超过阈值（默认 10%）→ 中止整个备份"。
严格照做的话，**3 个文件的备份里坏 1 个**就是 33% > 10%，整次中止。

失败率这个指标存在的意义是识别**系统性**故障（盘要坏了、权限整片没了），
样本数很小时它只是噪声。所以加一个下限：处理过的文件数低于它时只看"连续失败次数"。

### B3【必要】不进入目录重解析点，并把跳过的目录交出来

[03 §3](03-备份引擎.md) 要求 `AttributesToSkip = 0`（隐藏/系统文件也要备份，.NET 默认会跳过）。
但这会让 .NET 的递归**跟随目录符号链接 / junction**，遇到自引用链接就是无限递归。

所以 `PhysicalFileSystem` 自己实现递归（这本来也是必需的——文档要求按 exclude 规则剪枝，
而 .NET 的 `RecurseSubdirectories` 不提供剪枝回调）。规则：

- 文件的 `ReparsePoint`：照常备份（读它等于读目标内容）
- **目录的 `ReparsePoint`：不进入**
- 跳过的目录通过可选的 `IDirectorySkipReporter` 交出来，由引擎写进 `BackupLog`
  —— [03 §7](03-备份引擎.md) 的立场是"不静默"

### B4【必要】"先算哈希"路径的**写阶段必须重算哈希**

[03 §3.3](03-备份引擎.md#33-去重与哈希) 没点明这个坑：

> 先算哈希那条路径里，从"算完哈希"到"开始拷贝"之间文件可能又被改了。
> 若沿用第一次算出的哈希当 blob 名，就会写出一个**文件名与内容不符**的 blob——
> 而内容寻址的**全部**完整性校验都建立在"blob 名 == 内容哈希"上。
> 它会静默污染 blob 池，并被后续快照反复复用。

所以实现上"未命中 → 拷贝"这一步一律走**边拷边算**，并用**这次**算出来的哈希命名。
blob 永远自洽；代价只是多算一次哈希（CPU），不多读一次盘。

### B5【修正】逐文件失败处理的异常范围

[03 §7.1](03-备份引擎.md) 指出旧设计只 catch `IOException` 而 `UnauthorizedAccessException`
不是它的子类。实现里覆盖：`IOException`（含 `PathTooLongException`）、
`UnauthorizedAccessException`、`SecurityException`、`NotSupportedException`、`ArgumentException`。

**刻意不含 `InvalidOperationException`** —— 那通常是编程错误，不该被当成"文件读不了"吞掉。

### B6【必要】落库一律用 `CancellationToken.None`

取消发生时，`ct` 已经取消。若用它去写"快照已作废"这条事实，写入本身会抛
`OperationCanceledException` 并盖掉真正的原因，快照会永远停在 `InProgress`（只能靠下次启动自愈）。

同样地，**抢救清单与增量回收两步也用 `None`**：数据已经提交完了，
此刻被取消只会留下"快照说 Completed、调用方却收到取消"的不一致状态。

### B7【补充】SQLite PRAGMA

`journal_mode=WAL` + `synchronous=NORMAL` + `foreign_keys=ON` + `busy_timeout=30000`，
挂在"连接打开"这个钩子上（`SqlitePragmaInterceptor`）。

备份作业会做大量分批提交，回滚日志模式下每次提交都要 fsync。
`synchronous=NORMAL` 下掉电最多丢最后几个事务——而备份是可重跑的，
这与 [03 §3.5](03-备份引擎.md#35-writethrough-必须去掉) 去掉 `WriteThrough` 是同一个取舍。

`foreign_keys=ON` 是必须显式打开的：SQLite 默认**不**强制外键。

### B8【补充】外键删除行为设为 `Restrict`

EF/SQLite 默认是 `Cascade`。这个库里**从不硬删除**业务记录（决策 #12），
设成 `Restrict` 是为了让"某处误写了 `Remove(task)`"直接失败，
而不是静默 cascade 掉一百万个 `BackupFile` 行。

## C. 还原

### C1【必要】`RestorePlan` 只承载摘要 + 需要注意的条目

[06 §4.4](06-后端与API.md) 说预演要"返回将写入的清单与冲突明细"。
但整快照还原在百万文件下，把每个"将要写入"的文件都列出来会让**计划本身把内存撑爆**，
而 UI 真正需要的只是"写多少个 / 多少字节 / 哪些冲突 / 哪些不可恢复"。

所以：`RestorePlan` 带 `TotalCount` / `PlannedCount` / `Conflicts` / `Unavailable` / `PlannedBytes` 摘要，
`Entries` 在条目数 ≤ 5000 时全列、否则**只列需要注意的**。
`ExecuteAsync` **不依赖** `Entries` 做实际工作——它按请求流式重新选靶。

### C2【必要】blob 是否存在在**计划阶段**就查

[04 §1.6](04-还原与快照管理.md) 要求"批量还原时若有部分文件不可恢复，先明确列出受影响的文件，
让用户选择是否还原其余文件，不要静默跳过"。

等到执行时才发现，用户已经点了确认。所以计划阶段就 `File.Exists` 每个 blob
（一次存在性检查，不读内容，很便宜）；执行期若 blob 在计划与执行之间消失，也归类为
`Unavailable` 而**不是** `Failed`。

## D. 目录关系校验

### D1【补充】新增第 6 条规则 `BACKUP_INSIDE_RESTORE_ROOT`

[02 §7](02-存储与数据模型.md#7-目录关系校验) 的 5 条只禁止"还原根在备份目录之内"。
对称情形（**备份目录在还原根之内**）没被禁止，但一次"整快照还原到该根"就可能覆盖 blob 池——
属于静默数据丢失路径，成本极低，不值得放过。

## E. 配置与依赖

### E1【修正】`\\?\` 前缀**按需**添加

[01 §6.1](01-总体设计.md#61-长路径) 说"内部统一通过一个路径工具类构造 `\\?\` 前缀的绝对路径"。
实现改成**只在路径长度 ≥ 240 时**才加，因为 `\\?\` 会：

- 关闭路径规范化（`..`、正斜杠、相对路径全部失效）
- 让部分网络重定向器不认

对普通长度的路径无差别加前缀，等于把所有路径的行为都换成另一套语义，收益为零、风险不小。
超长路径仍然会被正确扩展（含 `\\?\UNC\`）。

### E2【修正】FzLib 实际只用到筛选规则

决策 #1 是"优先用上 FzLib"。但实现下来只有 **`FileFilterRule` / `FileFilterHelper`** 用得上：

| FzLib 类 | 结论 |
|---|---|
| `FileFilterRule` / `FileFilterHelper` | ✅ 复用（筛选语义完整沿用） |
| `FileCopyHelper` | ❌ 其 `WriteThrough` 行为正是 [03 §3.5](03-备份引擎.md#35-writethrough-必须去掉) 要去掉的 |
| `FileHashHelper` | ❌ 只接受**路径**，既绕不开 `IFileSystem`，也无法"边拷边算" |

哈希用 BCL 的 `IncrementalHash` 自实现（`IHashService`），不引第三方。

### E3【补充】安全修补（NU1903）

传递引入的两个包带已知**高危**漏洞，公网部署 + 高安全等级（[05](05-认证与安全.md)）不能留着，
显式提升：

- `SQLitePCLRaw.bundle_e_sqlite3` → `3.0.5`
- `System.Security.Cryptography.Xml` → `10.0.12`

另外把 `Microsoft.Extensions.*` 与 EF Core 对齐到 `10.0.9`（避免 NU1605 降级错误）。

### E4【补充】TOTP 不引额外库

ASP.NET Core Identity **自带** TOTP（`GetAuthenticatorKeyAsync` / `VerifyTwoFactorTokenAsync` /
`GenerateNewTwoFactorRecoveryCodesAsync`），恢复码也有内置支持。
所以不引 `Otp.NET`；二维码由前端渲染，后端只返回 `otpauth://` URI。

## F. 实现期发现的缺陷（已修）

供后续回顾：这两个都是**不报错、只静默产生错误结果**的 bug，靠单元测试抓到。

| # | 现象 | 根因 |
|---|---|---|
| 1 | 增量备份退化成"每个文件都是新增" | EF Core 把 `Guid` 存成**大写** TEXT，而 `Guid.ToString()` 是**小写** → 手写的 `WHERE TaskId = $task` 永远匹配不到 → TEMP 镜像表为空。修法：**把 Guid 对象直接交给驱动绑定**，不自己转字符串 |
| 2 | 墓碑记录写了，但镜像里文件还在 | 快照链用 `BeginTime >` 做区间筛选，同刻创建的快照被静默排除。见 [B1](#b1修正快照链的区间比较一律用-snapshotid不用-begintime) |

> 教训的同一句话：**不要手写驱动内部约定的表示形式，也不要依赖时间戳的严格单调性。**

## G. 抢救清单（02 §6）实现期的发现

### G1【修正】回收账本的 `lastPath` 在文档自身的前提上不可能总是有值

[02 §5.1](02-存储与数据模型.md#5-回收站) 的回收判定是：
**"没有任何记录（含软删除的记录）引用它"才可回收**。

[02 §5.2](02-存储与数据模型.md#52-回收账本) 要求账本记录每个被回收 blob 的"最后路径"，
理由是**"这些信息在软删除的记录里都是现成的，几乎零成本"**。

这两条**合起来是矛盾的**：可回收的 blob 按定义就查不到任何记录，`lastPath` 也就无从得知。

而且现实中 blob 变成垃圾的**主要来源恰恰没有记录**——崩溃残留：
blob 已经写进池子，而记录所在的那一批还没提交（[03 §7.4](03-备份引擎.md#74-崩溃)）。
这种情况下本来就不存在"它曾经是什么文件"。

**实现取"诚实"**：能查到就填，查不到就留空（`lastPath: null`），不编一个出来。
账本仍然有 `hash` / `length` / `movedAt`，用户在回收站里至少知道"这是什么大小、什么时候被移进来的"。

> 若你要求 `lastPath` 一定有值，只有两条路：(a) 放弃"软删除记录仍算引用"这条规则（会破坏
> "删快照后空间不释放、可回溯"的整个语义），或 (b) 为 blob 单独维护一份"最后一次使用路径"的索引。
> 都超出了 v1 的范围，请定。

### G2【修正】`_root` 作为保留片名会与真实目录冲突（已修）

[02 §6.2](02-存储与数据模型.md#62-落盘方式) 说片名是 `<一级子目录名>.json`。
实现期发现：源目录根下**直接**的文件没有一级子目录可用，只能另取一个保留名 `_root`；
但若源目录里真有一个一级目录叫 `_root`，两者会写到**同一个文件**上——**静默丢条目**。

已修：片名对真实段名做**单射转义**（`%`→`%25`，`_`→`%5F`），于是任何真实段名都不可能等于字面的
`_root`；普通名字（不含 `%` 与 `_`）完全不受影响，片名仍与文档一致。二级层的
`<一级>\_root.json` 同理。

### G3【补充】未被触及的清单分片，头部时间戳会停留在上一次写入的值

"只重写受影响的片"（[02 §6.2](02-存储与数据模型.md#62-落盘方式)）的直接推论：
一次增量没动到的片，其 `generatedAt` / `latestSnapshotId` / `latestSnapshotTime` 仍是旧的。
这是**有意的**（否则一次增量要重写全部片，百万文件下不可接受的写放大），但读者不能指望
任意一个片的头部都指向最新快照。

### G4【补充】虚拟全量的条目在清单里没有 `hash`，因此照清单无法还原

虚拟全量本来就不写 blob（[03 §1](03-备份引擎.md#1-快照模型)），所以它的条目只能如实写
`hash: null`（不丢条目、不伪造哈希）。

但这与"不需要本软件就能还原"这个清单目标是冲突的——**对虚拟全量的记录，这个目标在当前快照模型下达不到**。
清单层无法补救，属于上游模型的性质。UI 已按 [03 §1](03-备份引擎.md#1-快照模型) 的要求显著标注不可恢复。

### G5【补充】`BackupSnapshot.MirrorInconsistencyCount` 的实际语义

实现里它**不是**"镜像与记录逐条比对出的不一致数"——那需要 replay 整条链再比对，
正是 [03 §4](03-备份引擎.md#4-镜像重建) 禁止的做法。它的实际来源是：

- 正常路径：`0`
- 抢救清单生成时发现**链断裂**（解析不出目标快照所属的全量）→ 记为 `1`，
  且**一个清单文件都不写**（写一份缺条目的清单比不写危险得多），同时 `LogWarning`。

若你期望它反映真正的逐条比对结果，那需要一次代价与设计要求冲突的额外校验，请明确要不要做。

## H. Api / 宿主阶段

### H1【修正】`Response.Clear()` 会连 `Set-Cookie` 一起清掉 —— 写操作全部 400

统一错误体写入器为了"覆盖上游设过的状态码与 content-type"调了 `context.Response.Clear()`。
它看起来人畜无害，实际会把**全部响应头**清掉，包括 `Set-Cookie`。

而被清掉的那个 `Set-Cookie` 正是 antiforgery 令牌：安全方法（GET）上由中间件下发，
下一个写请求要靠它。于是：

> 客户端第一次请求（任何 GET）→ 服务端下发令牌 → **该响应若是错误（401 等）**
> → 错误写入器把令牌抹掉 → 客户端永远拿不到令牌 → **之后所有写操作（含登录）都 400**。

已修：清之前把 `Set-Cookie` 取出来，清完再放回去。**这条值得记住**——
`Response.Clear()` 是常见写法，而它清掉的信息里可能藏着"下一个请求能不能成功"。

### H2【修正】`SessionValidationEvents` 漏注册 —— 每个受认证保护的请求都 409

它被配成 Cookie 认证的 `EventsType`，认证处理器会从**请求容器**里
`GetRequiredService(EventsType)` 来实例化它，所以**必须**在 DI 里注册。

失败模式很迷惑：应用正常启动、日志一切正常、迁移与种子账号都成功，
但**每一个**受认证保护的请求都以 `409 + "No service for type …"` 结束。

### H3【修正】CSRF 是"配对令牌"模型 —— 前端不能照抄 Angular 惯例

> 这条**推翻了**本文档上一轮我给出的说法（"把 cookie 名配成 `XSRF-TOKEN`、
> 头名配成 `X-XSRF-TOKEN` 即可，前端不用改"）。那个说法是错的。

ASP.NET Core 的 antiforgery 下发的是**一对**令牌：

| 令牌 | 去处 |
|---|---|
| *cookie token* | `XSRF-TOKEN` cookie |
| *request token* | 由客户端放进 `X-XSRF-TOKEN` **请求头** |

校验时比较两者的**配对关系**。所以客户端**无法**从 cookie 值推出该往头上写什么——
Angular 那套"读 `XSRF-TOKEN` cookie 的值回填到 `X-XSRF-TOKEN` 头"在这里会得到
`The cookie token and the request token were swapped`，表现为**所有写操作都 400**。

**修正**：新增 `GET /api/auth/csrf`（匿名、安全方法）从**响应体**下发 request token：

```
GET /api/auth/csrf → { "token": "<requestToken>" }
```

### H3b【修正】令牌只能有**一个**签发点，且必须在认证之后

上面那条只是第一层。真正把"登录后所有写操作 400"坐实的是**签发点不唯一**：

那个"在安全方法上顺手签发令牌"的中间件**在管道里被注册了两次**——
一次在 `UseAuthentication` **之前**（第 ⑥ 步），一次在之后（第 ⑩ 步）。
注册在认证之前的那一次，让**每个 GET 都在用户还是匿名时签发/复用 cookie token**；
而写请求的校验发生在认证之后（身份是 `admin`）→ 报

```
The provided antiforgery token was meant for a different claims-based user than the current user.
```

**修法**：删掉那个中间件，令牌**只**由 `GET /api/auth/csrf`（在认证之后执行）签发。

**再叠一层保险**：身份变化后（登录成功 / 登出）服务端删掉 `XSRF-TOKEN` cookie、
前端清掉缓存的令牌——否则匿名期签发的令牌会被带进已登录状态。

**这条的教训值得单独记**：`antiforgery` 的失败模式是"**读操作全好、写操作全坏**"，
非常容易被误判成"只有保存坏了"而去查业务代码。而它的根因在**管道顺序**上。

### H3c【修正】必须关掉 axios **内置**的 XSRF 支持

前两条修完，浏览器里**仍然**是 `The cookie token and the request token were swapped`，
而同样的序列用 curl 手测**完全正常**。差异在客户端库：

> axios 默认自带 XSRF 支持（`xsrfCookieName: 'XSRF-TOKEN'` / `xsrfHeaderName: 'X-XSRF-TOKEN'`），
> 它会自己读 cookie、把**cookie 的值**塞进请求头，而且**在请求拦截器之后执行**——
> 于是把我们设的 request token **覆盖**成了 cookie token。对 ASP.NET Core 来说那正好是最错的值。

**修法**：两处都关（实例 + 全局默认，后者覆盖 `fetchCsrfToken` 用的裸 axios）：

```ts
axios.defaults.withXSRFToken = false
axios.create({ /* … */ withXSRFToken: false })
```

**这条的教训**：当"手测通过、浏览器不通"时，先怀疑**客户端库的隐式行为**，
而不是服务端。这次差一点就往"再换一套 CSRF 方案"那条路上走——
那条路会绕开真正的原因，并且把三处已经正确的东西一起改坏。

### H4【补充】`wwwroot` 必须显式声明 `CopyToOutputDirectory`

Web SDK 只在 **publish** 时处理 `wwwroot`。开发期直接运行 `bin` 下的 dll 时（内容根 = 输出目录），
不显式声明 `<Content Update="wwwroot\**" CopyToOutputDirectory="PreserveNewest" />`
就不会被复制，表现是**"接口全部能用、界面一律 404"** + 一条容易被忽略的
`The WebRootPath was not found` 警告。

用 `Update` 而不是 `Include`：Web SDK 已经隐式把 `wwwroot\**` 加为 `Content`，再 `Include` 会
`NETSDK1022 重复项`。

### J1【必要】全量快照必须丢弃脏目录

[03 §5.4](03-备份引擎.md) 要求局部扫描"只重扫变化目录，未变化目录继承"，
而 [03 §5.4](03-备份引擎.md) 同时要求"一个快照仍然覆盖整个源"。这两句在**全量**上会冲突：

监控触发时带着脏目录进来，而 `DecideNextType` 可能判定本次要跑**全量**
（还没有任何 Full、或增量数超过 `MaxAutoIncrementBackupCount`）。此时若沿用脏目录，
这个"全量"的镜像只含被扫到的那棵子树 —— 而它会被后续增量当作基准，链从此长期不一致，
抢救清单还会被重写成只剩那棵子树。

**实现**：`type != Increment` 时把 `dirtyScopes` 置空。语义上只有增量才有"继承上一个镜像"这回事。
**这条极容易触发**：任务刚开启监控、第一个快照之前正好有文件改动，就会走到。

### J2【必要】跳过的目录必须由引擎取走并写进 `BackupLog`

[B3](#b3必要不进入目录重解析点并把跳过的目录交出来) 写的是"跳过的目录通过可选的
`IDirectorySkipReporter` 交出来，**由引擎写进 `BackupLog`**"。B3 的后半句当时**没有实现**：
队列唯一的消费者是 `FsController` 那个私有实例，引擎侧的单例队列只入不出。后果：

- 用户永远不知道有子树没被备份 —— 快照照报"备份完成：失败 0"（03 §7 要的就是"不静默"）；
- **增量下更糟**：无法枚举目录里那些仍然存在的文件的旧镜像行不会被 `TakeBatchAsync` 取走，
  于是被当成删除写成墓碑 —— 镜像里文件消失，全程无提示；
- 队列随进程生命周期无界增长。

**实现**：`BackupEngine.RunAsync` 收口处 drain 并写 `BackupLog`；只有"无法枚举"计入 `FailedFileCount`
（有意跳过的重解析点若也计数，源目录里放几个 junction 就会让每次备份都显示成"成功（N 个失败）"）。
为此给 `SkippedDirectory` 加了 `Deliberate` 标志，不再靠 `Reason` 的字符串前缀分辨两类。

### J3【修正】"浏览已作废快照"与"还原已作废快照"必须分开对待

[02 §2.2](02-存储与数据模型.md#22-backupsnapshot--快照) 只说"查询一律只看 `Status == Completed`"，
没规定请求一个 Aborted/InProgress 快照时该给什么。实现是**静默回退到该快照之前的最后一个
Completed 快照**，并且有一个测试（`Aborted快照的记录不参与镜像重建`）把它固化成了有意行为。

复核发现这个回退在**还原**上是危险的：用户点开快照 #N、看着 #N 的预演结果点了确认，
实际写下去的却是快照 #M 的内容 —— 还原是写文件操作，写错时间点不可逆。

**修订**：浏览路径**保持原样**（回退是有意的，测试继续守着）；**还原路径加校验** ——
`RestoreService.ResolveAsync` 要求 `Status == Completed`，否则明确报错。
理由是这个方向是"更严格"而不是"换一套做法"，不需要推翻任何设计决定。

## K. 第二轮（再复核后）补上的

把修复清单回传给同一批子 Agent 做增量再复核，它们又找出 11 处，其中 **6 处是我自己的修复带出来的**
（含 2 处与修复前**同一类**的缺陷）。已修 8 处，其余如实列入下表的 K4。

### K1【必要】显式请求增量会绕过"超限转全量"，把链推过 SQLite 参数上限

```csharp
SnapshotType type = requestedType ?? await _chains.DecideNextTypeAsync(task, ct);
```

那个"增量数超过 `MaxAutoIncrementBackupCount` 就转全量"的决策，**只在调用方没有显式指定类型时**
才被咨询；而 `POST /api/tasks/{id}/backup` 可以带 `{"type":"Increment"}`。于是连续请求增量能把链
一路推过 32766 —— 然后镜像物化的 `IN (chainIds)` 参数过多，**该任务的增量备份与还原开始显式失败**，
直到有人手动跑一次全量把链重置。

**实现**：`BackupEngine.MaxIncrementChainLength = 20000`，超了就在同一条退化路径上转全量。
取舍与文件里那句"宁可多写一份数据，也不能写出一条 replay 不通的坏链"一致。
不依赖 `DecideNextTypeAsync` 被咨询过，所以也顺带守住了其它几处未分块的 `Contains`
（它们的入参都是"链"或"级联删除集合"，同受这个上界约束）。

### K2【必要】脏目录数没有**绝对**上限，只靠占比

镜像物化把每个脏目录写成 2 个 SQL 参数（`LIKE` + `=`），而脏目录数只受
`LocalScanDegradeRatio`（占比超过 30% 才退化全量）约束。源树目录数上万时，**30% 以内就能过万** ——
占比判据拦不住，而约 16384 个脏目录会让**增量备份以 SQLite 报错中止**。
这比 K1 明显：还原失败用户还能改范围，**备份失败是"核心功能在目标规模上停止工作"**。

**实现**：`MaxDirtyScopeCount = 8000`（依据：`1 + 链长 + 2N`，链长按被夹住的上界 10001 算也只有
26002 < 32766），超过就退化为全量扫描。**退化在语义上是免费的** —— 局部扫描只是省读，全量总是更完整。

### K3【修正】重解析点判据必须与"存在性"解耦

J 节之外的一处**实现期事实更正**（它推翻了我原先沿用的前提）：

| 情形 | `File.Exists` / `FileInfo.Exists` | `Directory.Exists` / `DirectoryInfo.Exists` |
|---|---|---|
| 悬空的**文件**链接 | **true**（属性带 `ReparsePoint`） | false |
| 悬空的**目录**链接 | true | **false**（所以 `GetDirectory` 返回 null） |

实测（.NET 10 / Windows 10）确认。于是：基于存在性的检查**看不见悬空的目录链接**，
而 `Directory.CreateDirectory` 与 `FileMode.Create` 都会**跟随**它 —— 白名单根里摆一个悬空
**目录**链接（junction 在 Windows 上**不需要管理员权限**）就能把还原写到白名单之外。

**实现**：给 `IFileSystem` 加了一个不跟随、也不看存在性的探针
`bool IsReparsePoint(string fullPath)`（`File.GetAttributes`），`FindReparsePoint`
对目标文件与各级祖先都用它。测试：`RestoreTests.还原拒绝穿过白名单里的悬空目录重解析点`
（内存文件系统加了 `AddReparseDirectory(path, dangling: true)`，悬空目录在
`DirectoryExists` / `GetDirectory` 里**装作不存在** —— 忠实模拟真实行为）。

> **这条的教训**：复核者提出的方向对，但它的事实前提是错的（它认为悬空**文件**链接也不可见）。
> 我建了真实的悬空链接去测，才发现真正的缺口在**目录**链接那条**完全不同的分支**上。
> **照它说的改会绕开真问题。**

## L. 登录简化为单密码（2026-09-23，用户要求）

`05-认证与安全.md` 把"强制 TOTP"写成核心决策（§2.2），`08 §3` 还把它列为验收项。
本节记录**用户明确要求推翻这一条**：登录改为"只输一个密码"。

### L1【修正】去掉 TOTP 全家与用户名输入

**改前的四层**：Identity（用户名 + 密码哈希 + 锁定）/ TOTP 强制两步验证（密钥、二维码、恢复码、未绑定即 403 的闸门）/ 会话登记表 / 配对令牌 CSRF。
**改后**：只砍掉第二层与"用户名由用户输入"这一点，其余三层原样保留。

- `POST /api/auth/login` 的请求体只剩 `Password`，返回 `CurrentUserDto`（原先的三态
  `Authenticated`/`RequiresTotp`/`RequiresTotpSetup` 与其驱动的"绑定页"整个消失）。
- 账号不再由用户提供，服务端按配置解析（见 L4）。因此**"用户名不存在与密码错误不可区分"
  那套抗枚举逻辑连同时间侧信道拉平（`TimingEqualizerUser` 与那句等价的 `HashPassword`）一并删除**——
  被枚举的对象已经不存在了。
- 删除：`TotpRequiredMiddleware` 整文件、`AppClaimsPrincipalFactory`（它只为追加 `fbt:totp` 一个 claim 而存在）、
  `totp/setup`、`totp/confirm`、`totp/recovery-codes` 三个端点、`CompleteRecoveryCodeLoginAsync`、
  `RequireCurrentPasswordAsync`、`RevokeOtherSessionsAsync`、`FormatKey`、`BuildAuthenticatorUri`、
  `SecurityOptions.RequireConfirmedTwoFactor`、`ApiErrorCodes` 的三个 TOTP code，以及前端的三步登录页、
  `RecoveryCodesDialog.vue`、路由守卫里的强制绑定重定向。
- 同一批删除里还有 4 组（首轮复核指出 L1 漏列，此处补齐）：`SecurityClaims.TotpConfirmed`（`fbt:totp`
  常量，它与 `AppClaimsPrincipalFactory` 住在**同一个文件**里，不是独立文件）、`Program.cs` 的
  `.AddDefaultTokenProviders()`（Identity 的验证器/恢复码令牌提供者，见 L7-3）、前端 `api/types.ts` 的
  四个 TOTP 类型（`LoginResult`/`TotpSetupResult`/`TotpConfirmRequest`/`RecoveryCodesResult`），
  以及 `stores/auth.ts` 的 `mustBindTotp` 计算属性与 `setupTotp`/`confirmTotp`/`regenerateRecoveryCodes` 三个 action。

### L2【补充】刻意**不**减的防护

用户要求"简单"，能简化的只有 TOTP 那一层。以下一个都没动，理由是它们不是"复杂度"而是"单密码的补偿"——

| 保留项 | 为什么单密码模式下反而更不能减 |
|---|---|
| 登录限流（每 IP 每 5 分钟 5 次） | 密码成了唯一的一道门，暴力破解是首要风险 |
| 账户锁定（连续 5 次失败锁 15 分钟） | 同上；且**动态码错误原先也计数**，那条防"密码已知 + 无限猜第二因素"的通道消失后，锁定是仅剩的节流 |
| Cookie 会话三层校验（安全戳 / 登记表 / 绝对过期） | 与 TOTP 无关，是"改密码即失效全部会话""单独踢出"的实现 |
| 会话登记表 + 会话列表 | 同上。改密码时它负责让其它设备**立刻**掉线（安全戳的校验有 30 分钟间隔） |
| 配对令牌 CSRF + 唯一签发点 | 与 TOTP 无关，是写操作的防护 |
| 审计日志 | 现在它是"登录尝试"的唯一留痕处（原先还有 `TwoFactorFailed` 一类事件） |

`ChangePasswordAsync` **完全没改**：它本来就只要求"已认证会话 + 当前密码"，不依赖 TOTP。
它就是"界面里能改密码"的全部实现。

### L3【补充】TOTP 的审计事件类型与映射保留不删

`AuditEventType` 的 `TwoFactorSucceeded`/`TwoFactorFailed`/`TwoFactorRebound`/`RecoveryCodeUsed`/`RecoveryCodesRegenerated`
（值为 2/3/7/8/9）与 `AuditEventNames`、前端 `auditEventLabels` 里的对应文案**全部保留、不再写入**。

理由：`AuditLog.EventType` 是 **int**。删掉枚举成员后 EF 仍能读入（CLR 枚举容纳未定义值），
但 `AuditEventNames.Name()` 会回落到 `type.ToString().ToUpperInvariant()`，历史行显示成 `"2"`、`"3"`；
`?eventType=TOTP_SUCCESS` 的筛选也会变成 400（`LogsController` 对认不出的名字**抛 400**，不静默降级）。
保留下来的成本只是几个死枚举成员，删掉的成本是**让历史审计记录变得不可读**——
而审计日志按设计是永久保留、不参与级联删除的。

> **首轮复核更正（2026-09-23）**：本节初稿的理由是"历史 `AuditLog` 行里的 eventType 仍是这些字符串，
> 删掉会让旧记录在审计页显示成原始英文码"——**这个前提当时不成立**：前端那两条标签的键写的是
> `TOTP_VERIFY_SUCCESS`/`TOTP_VERIFY_FAILED`，而后端映射出来的是 `TOTP_SUCCESS`/`TOTP_FAILED`，
> 从来就对不上，历史行本来就显示英文码。同类错键另有 5 个（`TASK_CREATE`/`TASK_UPDATE`/`TASK_DELETE`/
> `RECYCLE_BIN_EMPTY`/`LOGOUT`），并缺 `SETTINGS_CHANGED`/`RECOVERY_CODES_REGENERATED` 两条标签。
> 由于审计页的筛选下拉**直接由这张字典的键生成**，选中任何一个错键都会让后端返回 400。
> 已按后端 `AuditEventNames` 的真实字符串逐字对齐（含顺序），并同步了 `mock/fixtures.ts` 里同源的假数据。详见 L7-1。

### L4【必要】`SecurityOptions.EffectiveSeedUserName`：播种与登录必须用同一个账号名

原先 `IdentitySeeder` 自己兜底（`SeedUserName` 为空则 `"admin"`）。单密码模式下账号名成了
**唯一的账号来源**，两处各自兜底一旦漂移就会得到一个极难查的现象：
播种建的是 `admin`、登录按空串查 → 恒定 401，而用户看到的是"密码明明对却登不上"。

所以把兜底收成一个计算属性，两处共用：

```csharp
public string EffectiveSeedUserName => string.IsNullOrWhiteSpace(SeedUserName) ? "admin" : SeedUserName;
```

### L5【补充】已知代价：任何人都能把你锁在门外 15 分钟

改前，"连续 5 次失败"要触发必须先**知道用户名**（或者去猜）。
改后，账号名固定且由服务端自己解析，**攻击者不需要知道任何东西**，只要连续 5 次提交错误密码
就能让唯一账号进入 15 分钟锁定。这是一个真实存在的、由本次简化引入的 DoS 面。

用户已确认保留锁定（见 L2），所以这里只是**如实记录**，不修。若将来觉得烦，两条路：
放宽/关掉锁定只靠按 IP 的限流，或接受它（密码策略仍是 ≥12 位混合字符，正常用户碰不到锁定）。

### L7【修正】本轮独立复核（三个子 Agent 分角度）发现并处理的问题

复核方式：三个独立子 Agent 分别从"后端删除行为审计 / 前端 Vue 与死代码 / 契约与'说法对不对'"三个角度
审这一整批未提交改动，主 Agent 逐条验证属实性并修复。**L7-1 与 L7-2 是两个 Agent 各自独立发现的**。

**L7-1【修正】审计事件标签的键与后端不匹配 —— 审计页选到就 400（既有缺陷，本次改动把它的错误前提当成了成立）**

前端 `auditEventLabels` 的键与后端 `AuditEventNames` 的字符串有 7 处对不上、并缺 2 条：
`TOTP_VERIFY_SUCCESS`/`TOTP_VERIFY_FAILED`（后端 `TOTP_SUCCESS`/`TOTP_FAILED`）、
`TASK_CREATE`/`TASK_UPDATE`/`TASK_DELETE`（后端 `TASK_CREATED`/`TASK_UPDATED`/`TASK_DELETED`）、
`RECYCLE_BIN_EMPTY`（后端 `RECYCLE_BIN_CLEAR`）、`LOGOUT`（后端**根本没有**这个事件），

② 历史行由后端映射成正确名字，前端却只有错拼的键 → 走 `?? type` 兜底，**页面上显示原始英文码**。
一直没暴露是因为 `mock/fixtures.ts` 用的是**同一批错键**（mock 与前端自洽、与后端不自洽）。

已按后端真实字符串逐字对齐（顺序也照 `AuditEventType` 枚举），并同步了 mock 里同源的假数据。
**这也更正了 L3 初稿的理由**（见 L3 的更正块）——那条理由正是被这个错误前提支撑的。

**L7-2【必要】回车会发两次登录请求（本次改动引入的回归，已修）**

`el-form` 渲染的是裸 `<form>`。按 HTML 的隐式提交规则，"表单里没有提交按钮、且阻止隐式提交的
字段（文本类输入框）不超过一个"时，在输入框里回车会**提交表单**。删掉用户名框后表单里只剩密码
一个文本字段，于是回车同时触发隐式提交（`@submit.prevent`）与 `@keyup.enter` 两条路径。
改前有用户名+密码两个文本字段，隐式提交被抑制，所以只走一条路径——**这是"去掉用户名框"直接造成的**。

后者不是"多一次请求"那么轻：错密码会**双倍计数**（阈值 5 实际 3 次回车就锁号，而页面上的提示写着
"连续 5 次"），对密码会建出**两个会话**（会话列表里出现用户无法解释的幽灵条目，两个 Set-Cookie 互相竞争）。
已用 Playwright 实测确认（回车 2 次 / 点击 1 次），修法是把登录按钮移进表单、
`native-type="submit"`、去掉 `@keyup.enter`，两条路径合一；并在 `submit()` 加了重入守卫。

**L7-3【补充】`AddDefaultTokenProviders()` 的删除是静默的，留了警示注释**

删除本身无害（L1 已列，全仓已无 token provider 解析点），但 DI 的缺失**只在解析时失败、不在启动期**。
将来若加"邮箱确认"或"密码重置"，`UserManager.GenerateXxxTokenAsync` 会在**运行期**抛
`NotSupportedException`——正是被删那段注释警告过的失败方式。已在删除处留一行警示 + 何时必须加回来。

**L7-4【修正】`refreshUser` 变成死导出（本次改动造成的，已删）**

它的唯一调用者是被删掉的 `confirmTotp`。运行期无故障，但会让下一个读者以为"重新拉取当前用户"
是一条被支持的路径。已删除（连同 `return {}` 里的导出行）。

**L7-5【修正】`login()` 删掉了空响应兜底（已重建）**

原实现有 `if (!user.value) await bootstrap()`。新实现无条件置为已认证，于是"HTTP 200 但响应体为空"

## M. 浏览器全流程 e2e 发现并修掉的问题（2026-09-23，用户要求"全流程测一遍"）

做法：真实 Chrome（`channel:'chrome'`，无需下载浏览器）把 登录 → 设置 → 建任务 → 全量/增量备份 →
快照浏览 → 还原 → 完整校验 → 删除快照 → 回收 → 回收站 → 监控 → 日志 → 审计 → 会话踢出 →
删任务 → 登出 整条链走完；另起一个脚本专门验实时通道的**降级与恢复**。
判据一律取独立真相：本地重算 SHA-256 比对磁盘 blob、直接读 SQLite 文件，不信 App 自己说的"成功"。

结果：全流程 110 项断言全通过；降级/恢复探针 13 项全通过。下面 M1–M3 是这轮才暴露的真缺陷，
M4 是发现但**未**修的。**这些修复同样只有那个一次性脚本验证过，脚本未入库，不是可复跑的回归防线。**

### M1【必要】`PUT /api/settings` 静默丢弃还原根白名单

- `SettingsService.SaveAppSettingsAsync` 写了自动备份开关、深校验默认值、失败率阈值、保留策略，
  **唯独没写 `AllowedRestoreRoots`**；而读取路径（`GetAppSettingsAsync`）、控制器校验
  （`SettingsController.UpdateAsync` 的 `NormalizeRoots` + `ValidateRestoreRootsAsync`）、审计
  （`SettingsChanged`，detail 里逐字写明"还原根白名单：(空) → X"）全都在。
- 后果三连：① 用户点「保存设置」得到 200 与「设置已保存」，刷新即失效；② 白名单是还原的**硬约束**
  （04 §1.3），一条都存不进去 → 还原向导永远显示"白名单为空…否则无法还原"；③ **审计在说谎**——
  它记录了一次并未发生的变更，而出问题时第一个要查的就是它。
- 为什么没有测试兜住：`SetAllowedRestoreRootsAsync` 在生产代码里只有**一个**调用点（启动播种，`SettingsService` 的
  `SeedAsync`）；两个测试项目都是**绕过 API 直接调 store** 写白名单（`IntegrationHarness.cs:147`、
  `RestoreTests.cs:23`），`PUT /api/settings` 这条路径零覆盖。
- 修法：在 `SaveAppSettingsAsync` 里补上 `SetAllowedRestoreRootsAsync(settings.AllowedRestoreRoots ?? [], ct)`
  （该方法的唯一调用者就是 PUT 端点，不会误伤别处）。

### M2【必要】备份完成后任务详情页不刷新（`resyncTick` 少了一个信号源）

- `realtime.resyncTick` 只由 `onResync` 触发，而 reason 类型被限定为
  `'connected' | 'reconnected' | 'polling'`（`realtime/client.ts`，注释写明"重连后 / 每次轮询"）。
- `stores/tasks.ts` 的 `finish()`（`job.completed`/`job.failed`/`job.aborted`）与 `snapshot.committed`
  原先只调 `refreshQuietly()`——那只刷 store 自己的 `tasks`，**只有列表页受益**。
- 而 `TaskDetailView` 与 `SnapshotListPanel` **不读 store 的 tasks**，它们只 watch `resyncTick`。
- 后果：手动备份跑完后（实测备份本体只用了 **103 毫秒**），详情页停在「已排队 / 正在全量备份」、
  "上一次备份结果"为空、快照列表不出新行、「取消」按钮一直可点——**在健康的实时连接下永远不自己更新**，
  直到用户手按「刷新」，或实时通道恰好断开重连（那才会发 resyncTick）。实测停了 40 秒仍未更新。
- 修法：`finish()` 与 `snapshot.committed` 改为递增 `realtime.resyncTick`；列表页的刷新由 `App.vue`
  对同一 tick 的统一监听（`tasks.onResync()`）负责，因此**不会**重复拉取。

### M3【必要】快照表漏渲染全量快照行

- 接口按契约分组返回：`SnapshotGroupDto { fullSnapshot, snapshots[] }`，且 `snapshots` **只放增量**
  （`SnapshotsController.ListAsync` 的注释明确写了契约是"fullSnapshot + increments"）。
- `SnapshotListPanel` 的 `rows` 只平铺 `g.snapshots`，**把 `fullSnapshot` 整个丢掉了**。
- 后果：① 只做过一次全量、还没有任何增量的任务，快照 Tab 显示"没有符合条件的快照"——
  与任务卡片上的"快照 1 个（有效 1）"直接矛盾；② 全量无法「浏览文件 / 变更内容 / 删除」
  （操作列对行是无条件的，所以没有全量行就等于没有这些入口）；
  ③ 删除弹窗里写的"级联删除它到下一个全量之间的所有快照"对全量**永远够不着**。
  旁证：`类型` 列渲染的 `SnapshotTypeTag` 支持 `全量/虚拟全量/增量` 三种，但数据里永远只出现增量。
- 修法：`rows` 里先把 `g.fullSnapshot` 推成一行（组头），再推该组的增量（新的在上）。

### M4【未修】回收账本的 `lastPath` 没有任何生产者

- `IBlobStore.cs` 的 `BlobRecycleRequest.LastKnownPath` 与 `PhysicalBlobStore` 里
  `LastPath = request.LastKnownPath` 是**全仓仅有的两处**——没有生产者，永远为 `null`；
  界面上「移入前的最后路径」这一列因而永远显示「（未记录）」（02 §5.2 想要它来避免"盲删"）。
- **但它不是一行代码就能补的**：GC 的判据是"没有任何记录（含**软删除**的记录）引用它"，
  因此能进回收站的本来就只有手工拷进来的孤儿——那种情况下**本来就没有路径可记**。
  要让它有意义必须先动 GC 判据，属于设计决策，故本轮只记录不改。
- 顺带纠正一个易误判处：手工拷进 blob 池的孤儿在账本里 `lastPath` 为 `null` 并且界面显示
  「（未记录）」是**正确行为**（`PhysicalBlobStore` 的注释：账本里没有的仍然列出来，
  "待用户手动删除"不能变成"待用户盲删"）——断言这里不该写成"必须有值"。

### M5【补充】本轮**刻意未测**的两项

1. **连续 5 次错密码触发的账户锁定**：锁定 15 分钟且项目**没有解锁入口**（只能等），测它等于自伤。
   已验证的是"单次错密码 → 401 `LOGIN_FAILED` + 页内错误态"，以及成功登录会清零失败计数。
2. **真实修改密码**：会一次性作废全部会话（含当前会话），中途出岔子账号会停在未知状态。
   只验了校验分支（两次输入不一致）。会话失效机制改由「踢出」那条用例覆盖（被踢会话 `/auth/me` 立即 401）。

  它的**前提**是"目标机已装运行时"——而本项目实际要部署的那台生产机没有装，
  前提不成立，所以改发自包含：生产机零依赖，少一类"运行时版本/位数不对"的故障。
- 代价：包从约 5 MB 涨到约 110 MB。用户明确接受。

  这样文档 08 §4.1 对**手工发布**仍然成立，偏离只发生在有脚本托管的这条路上。

### N2【补充】单文件发布 + 关掉静态资源预压缩（488 → 55 个文件）

用户要求"publish 目录下文件可以少一点"，两项都实测过：

1. `-p:PublishSingleFile=true`：355 个 dll 合成一个 105 MB 的 exe。
   - 单文件最经典的陷阱是"靠物理路径定位资源"（`Assembly.Location` 在单文件下返回空）——
     **全仓没有一处** `Assembly.Location` / `AppContext.BaseDirectory` / `GetExecutingAssembly`，
     所以这个陷阱在本项目里不存在（已 grep 确认）。
   - 原生库**不能**被打进单文件，`e_sqlite3.dll` 必须留在 exe 旁边。
     少了它的症状很隐蔽：**能启动**，一碰数据库才炸。所以 `publish.ps1` 显式校验它存在。
   - 想退回传统多文件布局（便于逐个替换 dll 排查）用 `-MultiFile`。
2. `-p:CompressionEnabled=false`：关掉 Web SDK 的静态资源预压缩。
   - 它给每个前端文件额外生成 `.gz` 与 `.br`，38 个变 114 个。
   - **实测证据**：对同一个 js 资源，带 `Accept-Encoding: gzip, br` 与不带，
     返回的都是 57390 字节且**没有** `Content-Encoding` 头——预压变体一个都没被用到。
     原因是本应用用经典 `UseStaticFiles()`，它不做编码协商（那是 `MapStaticAssets()` 的行为）。
   - 所以这 76 个文件是纯死重。⚠️ 将来若改用 `MapStaticAssets()`，**必须去掉这个开关**，
     否则白白丢掉压缩收益。

### N3【补充】预压变体当时是**可以被直接下载**的

`GET /assets/<x>.js.gz` 返回 200 + `application/x-gzip`（`.gz` 在 MIME 映射表里，
所以 `UseStaticFiles` 会照发）。这不是漏洞（同源、内容本来就可公开、无秘密），
但它印证了 N2 的判断——那些文件确实只是躺在那里，没有任何协商逻辑在用它们。
现在关掉预压缩后这条路径也不存在了。

### N4【必要】ContentRoot = **工作目录**，所以 nssm 的 `AppDirectory` 是承重的

实测：把 `WorkingDirectory` 设成 `C:\` 启动发布好的 exe，应用**完全读不到配置**——
连 `appsettings.json` 都找不到（它不是按 exe 所在目录找的，而是按当前工作目录）。
症状极具误导性：**进程活着、端口无响应、日志目录压根没建出来**，
`DataDir` 会落到 `C:\App_Data`（并被权限拒绝）。

所以 `install-service.ps1` 里 `nssm set <svc> AppDirectory <安装目录>` 不是可选项。
（`DataDir` 用绝对路径是第二道保险，两者都要。）

### N5【补充】nssm 的 stdout/stderr 重定向目录必须在启动**之前**存在

nssm 在拉起进程之前就要打开重定向文件。若 `<DataDir>\logs` 不存在，服务直接起不来。
而应用自己的 Serilog 也往 `<DataDir>\logs` 写（06 §7）——两处都需要它。
`install-service.ps1` 因此先建目录再注册服务。

这两个日志也是**唯一**能看到"应用还没来得及配置 Serilog 就崩"的地方
（例如配置文件的 JSON 语法错误），所以脚本在启动验证失败时会把它们打出来。

### N6【补充】初始密码只在**建号那一次**被读取

`IdentitySeeder` 在账号已存在时直接 `return`，**不读**环境变量。所以：

- 升级/重启**不需要**再提供密码；
- 但**全新部署**缺密码时服务会拒绝启动（这是刻意的设计，不会自动生成密码）；
- `install-service.ps1` 因此在检测到「数据目录里没有数据库」且「没有密码」时**提前失败**，
  并把密码策略一起打出来——否则用户要去看日志才能猜出原因。

⚠️ nssm 把 `AppEnvironmentExtra` **明文**存在注册表里，所以脚本在首次成功后
提示把 `FILEBACKUPTOOL_ADMIN_PASSWORD` 那一条删掉（它已经没用了）。

### N7【修正】`__DATA_DIR__` 替换时必须转义反斜杠

JSON 里单个反斜杠是非法转义序列。把 `C:\ProgramData\FileBackupTool` 直接塞进模板

## O. 单元测试的偶发失败：钩子② 那条用例（2026-09-29）

### O1【必要】`钩子2_队列满时不丢事件而是反压并排一次全量扫描` 会偶发失败

**现象**：跑**整个套件**时偶发（本次会话共观察到 3 次）：

```
FileBackupTool.UnitTests.Monitoring.MonitorHookTests.钩子2_队列满时不丢事件而是反压并排一次全量扫描 [FAIL]
Assert.Single() Failure: The collection was empty
  MonitorHookTests.cs:line 114
```

单独跑这个类不复现，`dotnet test` 手工跑也不复现。所以**"198/198 全绿"从来不是一个稳定成立的说法**——
它只是大多数时候成立。

**代码层原因（确定的部分）**：测试等待的量，与它断言的东西之间隔了一步。

1. `ChangeEventQueue.Enqueue`（`ChangeEventQueue.cs:84-90`）：`TryWrite` 失败 →
   `Interlocked.Increment(队列反压计数)`（**第 89 行**）→ **之后**才
   `_onBackpressure?.Invoke(...)`（第 90 行）。
2. 回调 `ChangeMonitor.OnBackpressure`（`ChangeMonitor.cs:386-413`）：
   先 `foreach` 找到本根调 `root.NoteBackpressure()`（加**每根**计数——测试读的就是它），
   **再**判 `totalCount >= QueueBackpressureThreshold`，然后**在另一个 `foreach` 里**调
   `root.RequestBackpressureFullScan()`（置幂等标志）。
   **两步之间隔着一次阈值判断和一轮循环**（最初这里记成"两条相邻语句"，是记错了；
   窗口实际比那更大，结论不变）。
3. `RootMonitor.PumpAsync`（`RootMonitor.cs:252-261`）消费那个标志才会排全量扫描。

因此"计数已加、标志未置"是一个**真实存在的窗口**。测试只等计数、然后**只 pump 一次**；
这一次 pump 若落在窗口里，就什么也没排出来，`Assert.Single` 拿到空集合。

**产品侧不受影响**：标志是幂等的，下一轮 pump 必然消费
（`ChangeMonitor.OnBackpressure` 的注释写的就是"真正的扫描排程由单消费者在**下一轮**完成"）。
最坏情况是扫描晚一个 tick，绝不会漏。**所以这是测试的竞态，不是"会漏掉全量扫描"的缺陷。**

**改动**：把"只 pump 一次"改成"pump 到请求出现为止"（上限 40 次 × 5ms 的让出重试）。
断言**没有放宽**——仍是 `Assert.Single` + `IsFullScan`；产品若真的不排扫描，用例照样失败。

**⚠️ 但这是推断性修复，不是已证实的修复。** 本次做过 A/B 对照：
旧写法 `--no-build` 跑 12 次 + 带 build 跑 12 次，共 **24 次连续通过**，
**没能复现出抖动**，因此没有正面对照。保留它的理由是：那个窗口在代码里是确定存在的
（上面三步可逐行核对），而改动只是不再依赖"那一轮恰好领先于投递线程"，代价是一次有界重试。
若更倾向"没有证据就不改测试"，把那个 `for` 循环换回 `await h.PumpAsync();` 即可，其余不变。

**这条对发布脚本有直接影响**：`publish.ps1` 把"正退出码"一律判死（见 §N10），
所以这个 flaky 用例会让发布**偶发中止**。那是正确的失败方向（宁可停也不发一个"测试没过还发出去"的包），
但第一次遇到时要知道是它，而不是去怀疑自己刚改的代码。

### O2【补充】`TestWait.SchedulingYieldAsync` 早就写下了这一类坑

`tests/FileBackupTool.UnitTests/Monitoring/Fakes/TestWait.cs:24-34` 的注释：

## P. 让前端能挂在子路径下（2026-09-29，用户要求"想挂在 .../backup 下面"）

需求：不占用根路径，把应用挂到 `http://<内网机>/backup/`，再由外层公网服务器带 TLS 转发过去。

### P1【补充】**不加** `UsePathBase`，改用「前端 base + nginx 剥前缀」

先说结论：**后端一行没改。**

原本最直觉的做法是后端 `app.UsePathBase("/backup")`。没有采用，两个原因：

1. `Program.cs` 那条中间件管道是**顺序敏感**的，注释里逐条写着"顺序错了某项安全措施会静默失效"
   （ForwardedHeaders 必须最靠前、认证必须在限流之前、antiforgery 只能有一个签发点……）。
   为了一个部署形态去动它，风险与收益不成比例。
2. 有等价且更小的做法：让 nginx 把前缀**剥掉**再转发，应用收到的仍是他期望的根路径。

这个做法成立的前提是"客户端不会自己绕开前缀去找根路径的资源"，而它取决于一个必须实测的点：

**SignalR 的 `negotiate` 响应里**有没有**`url` 字段。**

- 若有，且是根相对（`/hubs/events?id=...`），客户端就会拿它去连**根**路径 → nginx 的
  `location /backup/` 不匹配 → WebSocket 连不上 → **静默降级成轮询**（功能还在、不报错、
  只是"实时"不再实时）。这是本项目最该避免的失败形态。
- 实测（`POST /hubs/events/negotiate?negotiateVersion=1`，已登录）**没有 `url`**：

  ```json
  { "negotiateVersion": 1, "connectionId": "...", "connectionToken": "...",
    "availableTransports": [ {WebSockets}, {ServerSentEvents}, {LongPolling} ] }
  ```

所以剥前缀是安全的：客户端只会用它被配置的那个路径（`VITE_HUB_PATH`）。

### P2【补充】改动清单（全在前端与构建脚本）

| 位置 | 改动 |
|---|---|
| `web/vite.config.ts` | 新增 `base: process.env.VITE_BASE \|\| '/'`（**全仓唯一**读这个变量的地方） |
| `web/src/router/index.ts` | `createWebHistory(import.meta.env.BASE_URL)`（原来是无参 = 根） |
| `web/src/api/http.ts` | `API_BASE` 默认值改为 `` `${import.meta.env.BASE_URL}api` `` |
| `web/src/realtime/client.ts` | `HUB_PATH` 默认值改为 `` `${import.meta.env.BASE_URL}hubs/events` `` |
| `publish.ps1` | 新增 `-PathBase`，在 `npm run build` **之前**只注入 `VITE_BASE` 一个变量 |

关键设计：**base 只有一个来源**。`vite.config.ts` 的 `base` 派生出的 Vite 内置
`BASE_URL`（总以 `/` 结尾）被 router、API 路径、Hub 路径共用，于是"页面 base"与
"接口/路由 base"在结构上不可能各自漂移。早先的写法是让三处各自读一次 `VITE_BASE`，
那存在错配成"资源能加载、一挂载路由就白屏"的可能。改成派生之后，构建脚本只需要注入
一个变量——注入的变量越少，"某处写错/漏改"的机会越小。

前端本来也只有这两处写死根路径（`API_BASE` / `HUB_PATH`），且已是环境变量驱动。
全仓没有 `window.location` / `href=` / `src=` 之类的硬编码。

### P3【必要】`publish.ps1` 在构建**之后**断言产物里的前缀

**先纠正一处记反的机制**（独立复核指出，已按本仓安装的 vite 8.3.0 源码核对）：
`loadEnv` 的**最后一步**是无条件
`for (const key in process.env) if (prefixes.some(...)) env[key] = process.env[key]`，
所以是 **`process.env` 胜出、`.env` 文件次之**——最初这里写的是"`.env` 优先"，
方向说反了。

（顺带一个会让人白写的坑：`vite.config.ts` 读的是 `process.env.VITE_BASE`，而 `.env`
文件的值不会被写进 `process.env`，所以 `web/.env.production` 里写 `VITE_BASE` 是
**无效**的。注意方向是安全的——它不会静默生效。）

断言仍然必要，但理由是另一条：**base 是构建期常量，脚本设了环境变量不等于 Vite 用了它**。
构建报成功而前缀没生效，症状是"部署上去白屏"，属于最难查的一类。所以构建后直接读
`web/dist/index.html`，断言它带（或不带）预期前缀、并且不存在"只生效一半"的混合引用，
对不上就 `Stop-Fail`。

`-SkipWeb` 与 `-PathBase` 设为**互斥**（前缀是构建期注入的，跳过构建不可能带上它）。

### P4【必要】两层代理下必须**透传** `X-Forwarded-*`，不能追加

这是本次最容易踩、且踩了也不报错的一条。

`Program.cs:393` 把 `ForwardLimit = 1` **硬编码**了（注释："只信任一跳：nginx 直连本进程"）。
实测（直接带伪造头打 127.0.0.1，它在 `KnownProxies` 里）：

```
X-Forwarded-For: 203.0.113.9                -> 应用记的 lastLoginIp = 203.0.113.9
X-Forwarded-For: 203.0.113.9, 198.51.100.7  -> 应用记的 lastLoginIp = 198.51.100.7   ← 取最右
```

所以"公网服务器 → 本机 nginx → 应用"这条**两跳**链上，本机 nginx 若用
`$proxy_add_x_forwarded_for`（追加），头上会变成 `<客户端IP>, <公网服务器IP>`，
应用取最右 → **它以为所有请求都来自公网服务器**。后果两条，都是静默的：

1. **登录限流退化成"全站共用一份 5 次/5 分钟"**——外面一台机器打你，你自己反而登不进去；
2. `X-Forwarded-Proto` 若被改写成 `http`，应用永远看不到 https → **不下发 HSTS**
   （05 §6.1 ④ 要求由应用下发）、Cookie 也不带 `Secure`。

正确写法是**透传**外层的值：

```nginx
proxy_set_header X-Forwarded-For   $http_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $http_x_forwarded_proto;
```

代价：任何能连到这一层的人都能伪造这两个头来绕过按 IP 的限流。若 `/backup/` 只该给外层
那台服务器访问，加来源限制即可（`allow <外层IP>; allow 127.0.0.1; deny all;`），
代价是失去了直接 `http://<内网>/backup/` 调试的便利。**这一条是权衡，不是定论。**

### P5【补充】nginx 还需要一条 `= /backup` 的精确匹配

`location /backup/`（带尾斜杠）**不匹配** `/backup`（不带斜杠），而不匹配就会落到根
location。所以要显式加：

```nginx
location = /backup { return 301 /backup/; }
```

### P6【补充】Cookie 的作用域没变

应用没有设 `Cookie.Path`，所以 `fbt.auth` 的 Path 是 `/` —— 在**外层公网域名**下它对整个
域名有效，不是只对 `/backup`。单用户系统里这不是问题，但如果那个域名上还挂着别的应用，
这个 Cookie 会一起发过去。

### P7【补充】验证状态：110/110 在 `/backup` 前缀下实测通过

不是"应该能跑"。做法：写了一个**忠实模拟那条 nginx location 的剥前缀反向代理**

关键几条：

### P8【必要】独立复核（一轮，10 条）发现并修掉的问题

## Q. 筛选规则被静默忽略（2026-10-01，用户要求"修掉这个缺陷"）

### Q1【必要】前端存的形状后端不认，规则被**静默丢弃**

前端把编辑器模型（`{whitelist,blacklist,useRegex}` × 文件/文件夹/路径）直接
`JSON.stringify` 存进 `BackupTask.FilterJson`；而库里与引擎认的是 **FzLib 的扁平形状**
（`IsEnabled/UseRegex/IncludeFiles/...`，见 [02 §2.1](02-存储与数据模型.md)、[03 §3](03-备份引擎.md)）。

`FilterRuleSet.FromJson`（`src/FileBackupTool.Core/Filtering/FileFilters.cs`）的容错策略是
"认不出就返回空规则"，而空规则等于**不过滤**。于是：界面上配好排除项、保存成功、
界面无任何异常，**备份却把源目录整个收了进去**。

这不是"某处转换写错"，而是**转换层根本不存在**——后端全仓（`src/`、`tests/`）搜不到一处
`whitelist|blacklist`。另一半同样致命：`IsEnabled` 前端从没写过，即便形状对了，
引擎侧那道 `rules.IsEnabled && !rules.IsEffectivelyEmpty` 的闸也会把规则挡掉。

**为什么一直没被发现**：控制器只校验"是合法 JSON 对象"，引擎只认自己的形状，两边各自
"正确"。它由独立复核在静态阅读中报出，随后实测证实（把界面形状的 JSON 直接 POST 给
`/api/tasks`，再对源目录跑筛选试算，返回的文件数与"不带规则"完全一致）。

### Q2【必要】多行分隔符：textarea 给 LF，后端按 CRLF 拆

`FileFilterHelper` 用 `Environment.NewLine`（Windows 上 `\r\n`）拆分多值
（本地 FzLib `FileFilterHelper.cs:65-85`；本仓 `FilterTests.多值用换行分隔` 已固化该行为），
而 `<textarea>` 按 HTML 规范给的是 `\n`。**即便形状修对了**，`*.txt\n*.jpg` 也会被当成
一条模式，永远匹配不上——同一个症状的第二个成因。故序列化统一 CRLF 连接（逐行 trim、丢空行）。

### Q3【补充】修复方向：统一到扁平形状（前端单点转换）

- `web/src/utils/filter.ts` 成为**唯一**的形状转换点（`parseFilterRule` / `serializeFilterRule`），
  组件不再自行 `JSON.stringify`；筛选试算也走同一个函数（试算看到什么，备份就是什么）；
- 保存时恒写 `IsEnabled: true`（界面没有"启用筛选"开关，填了条件就是要用）；
- 完全空规则仍序列化为 `null` → 后端归一化为 `{}`，保住 `BackupTask.HasFilter`
  靠 `!= "{}"` 判断"有没有筛选"的既有约定。

**否决的备选**：让后端接受嵌套形状——库里存的形状会与文档/FzLib/归档大师三处都不一致，
且因为 Q2 前端照样得改，省不下来，只多出一套长期维护的映射。
**不兼容旧的嵌套数据**（用户决定）：`parseFilterRule` 遇到旧形状得到空规则，开发期
mock 数据一并改成扁平。

### Q4【必要】后端加了门神：认不出的规则**必须报错**

新增 `src/FileBackupTool.Core/Filtering/FilterRuleValidator.cs`，保存与试算两条路径共用：

- 非空、但**存在不认识的字段** → `FILTER_RULE_INVALID`（400）；
- 判据是"**全部字段都必须认识**"，不是"至少认识一个"。后者会被旧形状蒙混过关：旧形状里的
  `useRegex` 与已知字段 `UseRegex` 大小写不敏感地撞名，"至少一个已知"成立 → 规则被当成
  "只有 UseRegex 的有效规则"，筛选内容照样整体丢失。**这条是被单元测试逼出来的**
  （第一版判据在 `认不出的形状必须报错而不是退化为不过滤` 上失败）；
- 字段类型不对、不是 JSON 对象、超过 64 KB 同样报错；
- 成功时返回**归一化**后的文本（字段名统一 PascalCase）——否则大小写不一的输入会被引擎侧
  区分大小写的 `FromJson` 读丢，又是一种静默退化；
- 归一化时"六个字段全空"一律写成 `{}`（见 Q3）。

校验放在 Core 而不是 Api：本仓测试项目不引用 Api，放 Api 就测不到。错误类别到 HTTP 的
映射在 `src/FileBackupTool.Api/Infrastructure/FilterRuleErrorMapper.cs`（新增），
保证保存与试算**说同一套话**。

### Q5【补充】正则模式下保存前试编译

新增 `FILTER_REGEX_INVALID`：`UseRegex=true` 时逐行 `new Regex(...)` 试编译，失败即 400
并指出字段名。它能防住一类更糟的失败：`*.txt` 这种通配符写法被当正则用时，`Regex` 会在
**备份跑到一半**时抛 `ArgumentException`——一条写错的规则炸掉整次备份。

**刻意不做**的：切换正则开关时自动把 `*` 转 `.*`（旧 FzLib 的 `FileFilterRule` 属性设值器
里有这个转换，但本仓直接反序列化，走不到那段代码）。属语义变更，需要单独设计。
