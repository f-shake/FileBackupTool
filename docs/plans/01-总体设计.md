# 01 · 总体设计

## 1. 定位

一个**服务端常驻**的文件备份工具。备份引擎跑在服务器上，浏览器只做控制面。

**要解决的问题**（按优先级）：

1. 备份要 7×24 常驻执行，不能依赖某台机器开着桌面客户端。
2. 备份源与目标都在服务器/NAS 上，桌面客户端反而是"远程端"。
3. 能从手机或其他电脑远程查看备份状态与历史（次要）。

**明确不做**：

- 不做多用户、不做协作、不做分享。
- 不做打包下载（**所有文件不出服务器**）。
- 不做与 ArchiveMaster 备份格式的兼容。

## 4. 进程模型与并发

### 4.1 全局 IO 作业队列（**核心约束**）

> **任何时刻，全局最多只有一个后台 IO 作业在运行。**

作业类型：**备份** 与 **还原**。

理由：

- 备份源与备份目标都在机械硬盘上，并发只会因寻道抖动而互相拖慢。
- 并发会让"某任务何时完成"完全不可预测。
- 还原若与同任务的备份并行，还原出来的文件会被正在跑的备份当成新变更**再备份一遍**；把互斥范围从"同任务"扩大到"全局"，规则更简单。

**实现**：单消费者 `Channel<IJob>` + 一个 `BackgroundService`。作业入队时记录排队位置，UI 显示"已排队，前面还有 N 个作业"。

**队列不跨进程重启恢复**：重启后 `InProgress` 的作业标记为 `Aborted`，用户重新触发。排队中的作业同理。

### 4.2 单个备份作业内部

- **文件处理串行**（机械盘，见上）。
- 但**枚举是惰性的**，且**哈希计算与拷贝在单个文件内部可以重叠**（`FileCopyHelper` 的读缓冲→Channel→写缓冲流水线）——这是唯一允许的并行形式。
- **数据库写入分批提交**：不能把整个快照的记录攒在 EF change tracker 里。工作线程产出记录 → Channel → 单消费者批量提交（批大小见 [08](08-测试与待定项.md)）。

### 4.3 变更监控

每个源目录一个监控器，运行在独立的 `BackgroundService` 中。监控器**不执行备份**，只产生"该根变脏"的信号并投递给脏目录合并器（见 [03](03-备份引擎.md)）。

### 5.2 数据库（业务数据，运行期）

**备份任务的定义存在数据库里**，以便在 UI 中即时增删改、与快照记录建立外键关联、并留下变更审计。

基础设施（连接串、数据目录、日志级别、信任代理、限流参数）留在 `appsettings.json`，天然支持环境变量覆盖。

> 对比：ArchiveMaster 把所有配置放在 `configs.json`。在单进程桌面下没问题；在 Web 下"改配置 + 进程重启 + 与数据库记录关联"三件事会互相咬。

## 6. 运行环境

| 项 | 决策 |
|---|---|
| 数据目录 | `App_Data`（相对应用目录，便携），**可通过配置覆盖** |
| 服务账号 | 开发期按"双击运行、当前用户"设计。nssm 部署时若需访问 UNC，改用有凭据的专用账号。**不要默认 LocalSystem** |
| 单实例 | **强制**。全局命名 `Mutex`（或锁文件）。nssm 下若误配成两个实例，两个进程会同时写同一批 blob 与同一个 SQLite——**静默毁数据** |
| 长路径 | 见下 |

### 6.1 长路径

源目录与还原目标都可能很深，必须处理。

**基线（必须）**：应用清单声明 `longPathAware`，并在部署文档中要求目标机器设置 `LongPathsEnabled=1`。

**目标（推荐）**：内部统一通过一个路径工具类构造 `\\?\` 前缀的绝对路径。

要注意的坑：

- `\\?\` 会**关闭路径规范化**——`..`、正斜杠、相对路径全部失效，必须传完全限定的路径。
- `FzLib` 的 `FileCopyHelper` / `FileHashHelper` 未必吃得下 `\\?\` 路径，需要包一层。
- 若目标机器未开启 `LongPathsEnabled`，超长路径会抛 `PathTooLongException`（它是 `IOException` 的子类），因此**会被逐文件失败处理吞掉，变成"静默跳过"**。这不可接受——必须计入快照的失败计数并在 UI 上显著提示。

## 7. 部署

### 7.1 构建

```
web:  npm ci && npm run build  → 拷贝到 src/FileBackupTool.Api/wwwroot/
srv:  dotnet publish src/FileBackupTool.Api -c Release
```

具体发布参数（自包含 / 单文件 / 裁剪）见 [08](08-测试与待定项.md)。

### 7.2 nginx 协同

nginx 终止 TLS，Kestrel 只监听 `localhost`。

**必须配置**：

1. **`ForwardedHeaders`**：否则限流与日志看到的全是 `127.0.0.1`，登录限流会退化成"所有人共用一份配额"。
2. **只信任 nginx 的 IP**（`KnownProxies` / `ForwardedHeadersOptions`）。`X-Forwarded-For` 可被客户端伪造，信任所有来源等于限流形同虚设。
3. **`UseHttpsRedirection`** 在反代后可能死循环——必须按 `X-Forwarded-Proto` 判断，或干脆关掉重定向、只依赖 HSTS。
4. **HSTS** 由应用设置，nginx 侧透传。

### 7.3 服务化

后续用 nssm 注册为 Windows 服务。当前按双击运行设计，因此：

- 数据目录用相对应用目录的 `App_Data`（便携）。
- 注册为服务后，**必须**把数据目录改为绝对路径（如 `%ProgramData%\FileBackupTool`），因为服务的工作目录与双击运行时不同。
