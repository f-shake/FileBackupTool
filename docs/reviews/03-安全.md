## 前提（用户已明确的安全约束，不是可选项）

| 约束 | 含义 |
|---|---|
| 公网可访问、**较高安全等级** | 默认不信任任何输入；不依赖"内网所以没关系" |
| **文件不出服务器** | 不存在任何形式的下载能力；前端也不该有下载入口 |
| **强制单实例** | 同一数据目录不能有两个进程同时跑 |

| **所有记录删除用软删除** | 不存在硬删路径 |

### S1：为什么这条最严重，以及修法的依据来自它自己的代码

把三条事实连起来看：①`GetAuthenticatorKeyAsync` **只读不写**，所以 `totp/setup` 返回的
就是**当前正在生效**的那把密钥；②`totp/confirm` 当时**只**校验动态码，不校验密码；
③它会调 `GenerateNewTwoFactorRecoveryCodesAsync` 整体作废用户手里那张恢复码纸。
于是"一个会话 Cookie"就换来了：长期密钥 + 把第二因素绑到自己设备 + 作废用户唯一的自救手段。

**修法不是我发明的，是同一份文件里已经确立的规则**：`totp/recovery-codes`（签发恢复码）
**要求密码**，而且注释明写"一个只有会话 Cookie 的攻击者不该能给自己签发一套永久钥匙"。
`setup` + `confirm` 达成的效果与它完全等价，却漏了这道校验——这是实现漏了一条，不是"可以更严"。

实现上把这段校验抽成了一个 `RequireCurrentPasswordAsync(user, password, detail)`，
`setup`（已绑定时）、`confirm`（已绑定时，且**提到任何状态变更之前**）、`recovery-codes` 三处共用。
它刻意**不**调 `AccessFailedAsync`：这是一条需要已认证会话才能到的路径，密码在这里是"二次确认"
而不是登录凭据，把打错密码算进锁定会让用户在设置页里把自己误锁。

前端只改了签名（`setupTotp(password?)` / `confirmTotp(code, password?)`）：登录页的**首次绑定**
流程不需要密码，行为不变；重绑本来就没有 UI 入口，所以这次修复**对现有界面零影响**。

### S3：哪些信号可分辨，我修了哪几个

原实现有三条可分辨信号：

| 信号 | 是否可分辨 | 处理 |
|---|---|---|
| 响应体 `detail`（不存在时 null，存在时"连续失败 N 次"+ 锁定阈值与时长） | ✅ 可分辨 | **已修**：401 不再带 detail，剩余次数只写日志 |
| **时间侧信道**（不存在时直接抛，存在时做一次 PBKDF2，差几十毫秒） | ✅ 可分辨 | **已修**：不存在的那条路径也做一次等价哈希（只为拉平耗时） |
| 已锁定 → 403 `ACCOUNT_LOCKED`（不存在时永远不会有这个响应） | ✅ 可分辨 | **保留**，见下 |

保留第三条是一个**有意的取舍**：单用户自托管工具里"账号被锁 15 分钟"必须让用户看得懂，
否则他只会看到"用户名或密码不正确"然后一直重试。它泄露的也只是"发生了锁定"——
攻击者自己把账号锁上，本来就知道。**账户锁定的 DoS 是 05 §4 选定的机制的固有代价**
（锁定按账户计数，换 IP 绕不过），现有的缓解是每 IP 每 5 分钟的登录限流。
要把这条也关掉，得改设计（例如锁定只对"已有失败记录"的账户生效），**交你定**。

### S2：为什么只查"已存在的段"就够

白名单校验是 `DirectoryRelationshipValidator.IsWithinAllowedRoots`——**纯字符串比较**
（那个文件的 usings 里连 `System.IO` 都没有）。而 `Directory.CreateDirectory` 和
`FileMode.Create(path)` 都会**跟随**重解析点。所以只要白名单根里有一个目录 junction，
或目标位置上已有一个文件符号链接，写入就会落到白名单之外。

修法是逐段上溯检查：**目标文件自身**（已存在的符号链接会被 `FileMode.Create` 截断它指向的真实文件）
+ 各级**已存在**的祖先目录。不存在的中间目录是我们自己创建的，新建目录不可能是重解析点，
所以查到第一个不存在的目录就能停。跨条目共享一个"已确认干净"的目录集合，
否则百万文件的整快照还原会做百万次 `GetDirectory`；加上之后每个**目录**只查一次。

命中时返回 `Unavailable` 并给出明确原因 —— 它会出现在**预演**里（04 §1.6 要求的"不静默"），
而不是等到写了一半才发现。

### 已逐条核对、判为 REFUTED 的点（记下来是为了下次不必重查）

子 Agent 自己列了一批它核对后**没有**报的点，我抽验了其中几条，结论一致：

- **反代信任**：`KnownProxies.Clear()` 后只加 `127.0.0.1`/`::1`，`ForwardLimit = 1`，
  客户端伪造的 `X-Forwarded-For` 取不到真实 IP（nginx 的 `$proxy_add_x_forwarded_for` 把真实 IP 放最右）。
- **CSRF**：类级 `[Authorize]` + 类级挂 `RequireAntiforgery`，登录这个 `[AllowAnonymous]` 写端点也过校验；
  `withXSRFToken: false` 两处都关；SignalR 不在 MVC 滤镜覆盖内，但 `SameSite=Strict` 让跨站握手带不上认证 cookie。
- **"文件不出服务器"**：全仓库搜 `PhysicalFile|FileStreamResult|Results.File|Content-Disposition|OpenRead|
  application/octet-stream` **零命中**，没有任何下发文件内容或 blob 流的端点。**这条是用户明确的安全要求，
  它成立。**
- **静态文件暴露面**：`UseStaticFiles()` 未换 FileProvider，只服务 `wwwroot`；`App_Data`（含密钥环）在它之外。
- **TOTP 重放窗口**：Identity 的 `VerifyTwoFactorTokenAsync` 接受 ±1 个时间步（约 90 秒）且无"已用码"缓存。
  要利用仍需密码 + 实时截获动态码（典型中间人钓鱼），05 §2.2 只要求"恢复码一次性"、未要求防重放
  → 判为**设计内已知取舍**，未上报。

## 第二轮：S2 的残留（以及我写错的一个前提）

再复核时那个子 Agent 指出 S2 有残留，理由是"悬空的文件符号链接在 `File.Exists` 眼里**不存在**，
所以检查会判它为空、随后 `FileMode.Create` 跟随它写穿"。**我没有采信，而是去实测**——
因为这条判据决定我要不要改接口。在本机建的悬空链接上（.NET 10 / Windows 10）：

```
悬空【文件】链接：File.Exists = True   FileInfo.Exists = True   Attributes = Archive, ReparsePoint
悬空【目录】链接：Directory.Exists = False   DirectoryInfo.Exists = False   File.Exists = True
```

**它给的前提是错的**：悬空的文件链接 `FileInfo.Exists` 返回 **true**，属性里带 `ReparsePoint`，
所以我原来那句 `_fs.GetFile(targetPath)` 的检查**本来就拦得住**；`BuildAlternativePath`
的 `!FileExists(candidate)` 也不会误选它（它被算作"存在"）。所以它说的那两条逃逸都不成立。

**但它由此推出的方向是对的**，只是打偏了一格：真正漏的是**悬空的目录链接**——
`DirectoryInfo.Exists` 对它返回 `false`（所以 `GetDirectory` 返回 null，我的祖先链检查看不见它），
而它**仍然**是重解析点，`Directory.CreateDirectory` 与 `FileMode.Create` 都会跟随它。
**目录 junction 在真实 Windows 上不需要管理员权限**，所以这不是纯理论情形。

### S2b【已修】判据必须与"存在性"解耦

给抽象加了一个不跟随、也不看存在性的探针：

```csharp
bool IFileSystem.IsReparsePoint(string fullPath);   // File.GetAttributes(…).HasFlag(ReparsePoint)
```

`FindReparsePoint` 现在对目标文件与各级祖先都用它，不再经过 `GetFile` / `GetDirectory`。
这也顺带把非悬空的情形统一了（原来要分别看文件属性和目录属性）。

**测试**：`RestoreTests.还原拒绝穿过白名单里的悬空目录重解析点` ——
内存文件系统加了 `AddReparseDirectory(path, dangling: true)`，悬空的目录在
`DirectoryExists` / `GetDirectory` 里**装作不存在**（忠实模拟真实行为），而 `IsReparsePoint` 仍返回 true。
断言预演阶段就把它标为 `Unavailable`、且执行阶段不写入。**这条测试在修复前必然失败。**

> 这一册的教训独立于其它几册：**复核者的前提也要验。** 它把"悬空链接"当成"文件链接也不存在"，
> 方向对、事实错。如果我照它说的去改（换成枚举父目录的属性），会**绕开真正的缺口**
> ——因为文件名在那条路径上是对的，问题在"目录链接"这个完全不同的分支上。
> 与 E7 那次一样：**能用一次实测定案的事，不要靠推理。**

### S4b【已修】落库失败的响应要说明"已经生效"

子 Agent 指出：`InvalidOperationException` 被 `ApiExceptionMiddleware` 映成 409，
而两个复合调用点（改密码、重绑）会在**已经改了状态之后**才报错 ——
用户看到 409 会以为"没改成功"而用**旧密码**重试。

**修法**：换成一个专门的 code `SESSION_PERSIST_FAILED`，文案明确写
"会话**已在内存中撤销**（该会话立即失效），但登记表落库失败——重启后可能恢复，请复核"。

### S5b【已修】那个 cookie 没有理由对脚本可见

同一处子 Agent 顺手指出：`Program.cs` 里 `options.Cookie.HttpOnly = false` 的注释写着
"前端要靠 `document.cookie` 取它" —— **那句话已经过时**：前端读的是 `GET /api/auth/csrf`
的响应体，而 axios 内置的读 cookie 行为是用 `withXSRFToken: false` 明确关掉的（09 H3c）。
配对令牌模型下 cookie 里那个 *cookie token* 本来就不需要 JS 看见（校验时服务端自己读）。

**改成 `HttpOnly = true`** 并重写了注释。这是纯收益：XSS 读到它也拿不到 request token，
而关掉读取面是纵深防御。**这一条需要一次浏览器验证**（登录后 DevTools 里
`XSRF-TOKEN` 应当仍存在且不可被 JS 读，且写操作仍能成功）。
