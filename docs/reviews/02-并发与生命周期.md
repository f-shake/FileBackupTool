## 判据：本角度的失败模式

| # | 要问的问题 | 违反的后果 |
|---|---|---|
| C1 | 有没有 **Singleton 捕获 Scoped**（尤其 `AppDbContext`）？ | 长期存活的实例持有一个已释放的上下文；表现为偶发 `ObjectDisposedException` 或跨请求串数据 |
| C2 | 单例里有没有**可变字段**被并发写？ | 数据竞争；在压力下才现形 |
| C3 | 作业队列入队用的是 `WriteAsync` 还是 `TryWrite`？ | `TryWrite` 在满时**丢作业且不报错** —— 这正是监控协作契约的**钩子②**，要求用 `WriteAsync` 形成反压 |
| C4 | 后台服务的未捕获异常会怎样？ | .NET 6+ 默认 `StopHost`：一个服务的 bug 让**整站**静默退出 |
| C5 | 有没有**丢唤醒**窗口（先检查条件、后进入等待，中间状态变了）？ | 任务永久挂着，无日志 |
| C6 | 取消发生时，清理路径是否也依赖那个已取消的 `ct`？ | 清理本身抛异常 → 状态卡在 `InProgress`，只能靠下次启动自愈 |
| C7 | 监控的三个钩子是否都接上了：① watcher 出错 → 立即全量扫描；② 队列反压；③ 启动 → 无条件全量扫描 | 变更被静默漏掉（备份不完整，且用户无法察觉） |
| C8 | 全局串行 IO 作业队列是否真的**同一时刻只有一个**作业在跑？ | 源盘与目标盘都是机械盘，并行 = 寻道互相打断，吞吐反而崩 |
| C9 | `FileSystemWatcher` 的事件缓冲溢出（`InternalBufferOverflow`）是否当作钩子①处理？ | 溢出即丢事件；若不降级为全量扫描，变更永久丢失 |
| C10 | `SemaphoreSlim` / `Channel` / `Timer` 是否正确释放？ | 句柄泄漏；长跑进程慢性死亡 |
| C11 | `async void` / 未 await 的 `Task`？ | 异常无人接收 → 进程崩溃（`async void`）或静默吞掉 |

## 发现与判决

8 条，**全部属实并全部修复**。这个角度的问题有一个共同特点：正常路径下**完全看不出来**，
只在特定的时序窗口里爆发，而且爆发时的症状离根因很远（"所有作业都排不进来"、
"点了恢复实时反而退回轮询"、"取消成功了却在跑"）。

| # | 发现 | 严重性 | 判决 | 处理 |
|---|---|---|---|---|
| C1 | **投递被取消 → 脏目录永久丢失**。`catch (Exception ex) when (ex is not OperationCanceledException)` 恰好排除了最可能发生的取消路径，而那句注释写的正是"投递失败不能把脏目录弄丢" | 🔴 | ✅ 属实 | **已修**：OCE 单独 catch，同样回滚后原样重抛 |
| C2 | **`job.started` 的发布在逐条目 try 之外** → 一抛异常就从 `await foreach` 逃出，**唯一的消费循环永久死亡**；而 `Status` 已是 `Running`，`IsBusy` 永远为真 → 此后所有备份/还原都排不进来 | 🔴 | PLAUSIBLE（结构确定，触发需要发布器抛异常） | **已修**：发布移进 try + 新增永不抛出的 `TryPublishAsync` |
| C3 | `CancelAsync` 与消费循环对 `Status` / `Cancellation` **零同步** | 🔴 | ✅ 属实 | **已修**：状态迁移与 CTS 的读写全部用 `_gate` 串行化；`Cancel()` 与 `Dispose()` 在同一把锁内 |
| C4 | `Status = Completed` 写在发布**之前** → 发布抛异常会把一次**已提交成功**的备份改写成 `Failed`（库里 Completed、界面 Failed） | ⚠️ | PLAUSIBLE（与 C2 同一触发面） | **已修**：`TryPublishAsync` 不再抛 |
| C5 | **`SessionRegistry` 读路径不持锁**，与写路径共享同一个 `Dictionary`（`IsValid` 在**每个受认证请求**上执行） | 🔒 | ✅ 属实 | **已修**：`Get` / `IsValid` 进锁（`Loaded` 的读也一并进） |
| C6 | 启动自愈与监控的钩子③并发 → 自愈会把**正在运行的合法备份**的快照标成 `Aborted` | ⚠️ | PLAUSIBLE | **已修**：自愈注册提到监控与作业队列之前 |
| C7 | `ChangeMonitor.Dispose` 在他人可能仍持锁时释放 `_pumpLock`（无 `_disposed` 保护） | 🔧 | PLAUSIBLE | **已修**：入口短路 + 吞 ODE + `ReloadAsync` 的 `_disposed` 检查 |
| C8 | `SessionValidationEvents` 用 `DateTime.UtcNow` 而非 `IClock` 判绝对过期 | 🔧 | ✅ 属实 | **已修**：注入 `IClock` |

### 三条值得单独说明的

**C1：注释与实现相反。** 那句话（"投递失败不能把脏目录弄丢：它们代表'磁盘上确实变了'这个事实"）
写得完全正确，而上面那行的异常过滤器把最可能发生的失败模式（请求被中止 / 宿主停机）
排除在外。`TakeReady` 已经把脏目录从 `_scheduled`/`_pending` 摘走放进 `_inFlight`，
不回滚它们就**永久消失**——要等这些文件再次被改、或 6 小时兜底全量扫描、或下次重启。
这类"注释是对的、代码是错的"比单纯的笔误危险，因为它让读者以为已经处理过了。

**C3：为什么 `Cancel()` 敢放在锁内。** 直觉上"持锁调用可能触发回调的 API"是死锁高发区，
所以这里必须给出理由：取消回调只是让引擎那侧的 `ThrowIfCancellationRequested` 生效，
**没有任何回调会回头抢 `_gate`**，所以不存在环。放进去换来的是一条硬保证——
"读到 CTS"与"释放 CTS + 置 null"不可能交错，于是那个窄窗口的 `ObjectDisposedException`
（表现为"点取消返回 500"）被彻底消掉。

**C6：靠顺序而不是靠标记。** 我没有给自愈加时间戳/Id 阈值，而是利用一个更强的性质：
`IHostedService.StartAsync` 按注册顺序依次 await，而"本进程创建出一条 `InProgress` 快照"
**只有一条途径**——作业队列的消费循环真的开始执行备份。把自愈挪到 `JobQueueService` 之前，
本进程就不可能在自愈期间创建出 `InProgress` 行。这比加阈值更彻底，也不用碰业务逻辑。
（代价：注册顺序成了一个**有语义的**约束，所以我在 `Program.cs` 里把那句"必须注册在……之前"
连理由一起写成了注释。）

## 第二轮：8 / 8 FIXED，且它确认了我最担心的那件事

再复核时子 Agent 给出 **8 条全部 FIXED**，并把每条的核对证据连行号一起给了。
它还专门回答了我追问的那个问题，以及一条我没想到的依赖。

### 一、"持锁调用 `CancellationTokenSource.Cancel()` 有没有死锁环"—— 它确认**没有**

这是 C3 里唯一让我不确定的地方（直觉上"持锁调用会触发回调的 API"是死锁高发区）。它的论证：

> `Cancel()` 的回调是**同步跑在取消方（HTTP）线程**上的，所以要成环，就必须有人在等
> *那个持锁线程*放锁 —— 而消费循环持 `_gate` 的两处**内部都没有 await、也没有持任何别的锁或信号量**，
> 它在等 `_gate` 时手里空无一物。取消回调能触到的只有 EF/SQLite 的 `DbCommand.Cancel()`、
> `FileStream`/`ChannelWriter` 的取消注册、以及 `ct.ThrowIfCancellationRequested`（纯标记，不抢锁）。

**这个论证的形式是对的**：死锁需要环，而"持锁者不等待任何东西"就切断了环。
它也顺手把回调能到达的所有代码列了出来，而不是只说"我看了，没问题"。

### 二、它列出两处**残留**，我采纳了其中一条

| # | 残留 | 处理 |
|---|---|---|
| C3a | 终态写入（Completed/Aborted/Failed）仍在 `_gate` **之外**，所以一个**极晚**到达的 `CancelAsync` 理论上会对已完成的作业返回 `true`（用户看到"已取消"，作业实际已完成并发了 `job.completed`）。纯显示层不一致 | **未修**，记录。修它要让循环的终态写入也进锁 —— 会扩大持锁范围，收益只是一个显示层不一致，不值 |
| C3b | `Cancel()` 会把回调抛出的异常聚合成 `AggregateException` 抛出（`lock` 会正常放锁，**不会死锁**，但异常会从 HTTP 路径冒成 500）。这是**原来就有的**性质，与本次加锁无关 | **未修**，记录 |

### 三`job.started` 那处的同类残留：它指出 `job.queued` 与进度事件仍是裸发布

它核对后判"无实际危害"（既不 await 也不在 try 内，异常只会变成无人观察的 Task，
且 SignalR 层已吞非 OCE），只是建议一致性。**未改**——那两处的调用点没有 `entry` 上下文，
为此改动签名不值得。

### 四、`BackupRunResult.Canceled` 这个分层它认为**对，而且比另两种做法好**

它给了三条理由，其中两条是我没想到的：

1. 与"用 `AbortReason == "用户取消"` 字符串比对"相比，显式标志不是 **stringly-typed** 契约；
2. 与"引擎在 `CancellationToken.None` 写完之后重新 `throw`"相比，那需要把 `RunAsync` 里
   从"跳过目录上报"到"构造结果"**整段**从 try 里挪出来，改动面远大于加一个字段；
3. `Canceled` 是新增属性，`SignalRJobEventPublisher.Summarize` 不读它，
   `JobView` 暴露的 JSON 只是**加字段** → 对既有前端契约向后兼容，不用动 `web/`。

**它提的第一条硬化我采纳了**（这一册唯一的第二轮代码改动）：

```csharp
// 原来：catch (OperationCanceledException) when (linked.IsCancellationRequested)
// 现在：catch (OperationCanceledException) when (linked.IsCancellationRequested
//                                                || entry.BackupResult?.Canceled == true)
```

理由：在此之前，"引擎置了 `Canceled`"⟹"过滤器放行"这个等价关系只由**跨层约定**维持
（靠注释）。哪天引擎新增一个用别的令牌（例如内部超时 CTS）取消、也置 `canceled = true` 的分支，
那个 OCE 就匹配不上过滤器，作业会变成 **Failed + "OperationCanceledException: 已取消"** ——
一个"说取消却报失败"的误导状态。绑定之后，只要引擎说 `Canceled`，作业就一定落到 Aborted。

**它提的第二条（别用异常表达"预期结果"、改成"结果 → 作业状态"的纯函数）我没有做**：
那需要把 `ExecuteAsync` 改成返回一个可选结果、并调整循环的终态与事件发布，属于结构性重构。
当前行为是**正确的**（作业确实变成 Failed 并带上原因），只是 `entry.Error` 会带上
`InvalidOperationException: ` 的类型名前缀，属于文案噪声。记在 09 J5 里等下一轮。

### 五、它指出 C6 那条保证依赖一个**默认值**，这是本轮最该记住的提醒

`StartupSelfHealService` 提前注册之所以成立，靠的是
**`HostOptions.ServicesStartConcurrently == false`（默认值）**：

> 哪天有人为了加快启动把它设成 true，保证会**静默消失**（注释保不住它）。

它还补充了这条保证的一个附加价值：它顺带挡住了"崩溃后 PID 被复用 → `SingleInstanceGuard`
误判为无实例 → 两个进程共用一个库"这种边角情形（那时自愈确实会扫掉**别人**正在跑的
`InProgress` 行）。**但那个情形下提前注册也救不了**（那是另一个进程），所以这条只是"顺带"。

**处理**：把这条依赖写进了 README 的"仍然没有做的事"里（见那里的 C6 注记），
并且**没有**改成阈值过滤（C6 那节解释过：靠顺序比靠阈值更彻底，且不碰业务逻辑）。
若将来真要把它变成不依赖默认值的硬保证，可选项是"自愈完成前标志位"或
"给 `AbortStaleInProgressAsync` 的查询加年龄过滤"——两者都记进了 09 J5。
