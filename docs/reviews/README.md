## 判定口径

子 Agent 的每条发现都按 `updating-code-review` 的口径给判决：

- `CONFIRMED` —— 确实存在
- `PLAUSIBLE` —— 在合理运行状态下可达（**默认判决**，不因"推测性"驳回）
- `REFUTED` —— 事实错误 / 不可能到达 / 已被别处处理

主 Agent（我）对每条**独立判断属实性**（先 grep/read 验证，不轻信子 Agent 结论），
分三类处理：✅ 属实 → 修；❌ 不属实 → 说明原因，不改；⚠️ 部分属实 → 按实际情况处理。

**已记录在 [09-实现期修订](../plans/09-实现期修订.md) 里的偏离不算 bug**，
除非那条记述本身与代码不符——那属于"文档写错了"，要改文档。

## 各分册的构成

每个分册都有固定的四节，**前两节不依赖子 Agent 的结论**，所以先立着：

| 节 | 内容 | 什么时候写 |
|---|---|---|
| 复核范围 | 本角度看哪些目录/文件 | 复核开始前 |
| **判据** | 本角度要守的**不变量 / 失败模式清单**（带编号，供逐条引用） | 复核开始前 |
| 发现与判决 | 子 Agent 的每条发现 + 我的属实性判决与理由 | 阶段二 |
| 修复记录 | 实际改了什么、怎么验证的 | 阶段二 / 三 |

**判据那一节是刻意先写的**：它把"什么算问题"在我看到任何发现**之前**就固定下来，
避免被具体发现牵着走（看见一个 bug 就觉得到处都是 bug，或者反过来因为某处
"看起来有设计意图"就一律放过）。判据里的每条都注明出处——要么是 `01`–`08` 的契约，
要么是 `09` 里已经踩过的坑。

### 这次复核最该记住的四件事

1. **两份报告结论相反时，去实测。** "EF 会不会把 `Contains` 内联成参数"这一条，两个 Agent 给出了
   **相反**的断言，而它决定一个端点会不会在快照数超过 32766 时直接崩。我用 `ToQueryString()` 量了
   （10 个 → 899 字符、5000 个 → 307045 字符），把结论写成了**常驻测试**而不是留在文档里。
   → 那条被证伪的 Agent 随后自己复核并接受，还从我的数据里反推出"约 61 字符/元素"的斜率来佐证。
2. **复核者的前提也要验。** 同一个 Agent 提出的"悬空链接逃逸"方向是对的，但它的事实前提是错的
   （它说悬空链接的 `File.Exists` 返回 false，实测返回 **true**）。我建了真实的悬空链接去测，
   发现真正的缺口在**目录**链接那一条完全不同的分支上。**照它说的改会绕开真问题。**
3. **"注释是对的、代码是错的"最危险。** 并发册 C1 那条，注释写着"投递失败不能把脏目录弄丢"，
   而上一行的异常过滤器恰好把最可能发生的失败模式排除了。
4. **有意为之的设计决定，不该在复核里顺手改掉。** Aborted 快照的浏览回退有测试守着，我没有推翻；
   只把**还原**那条路改成明确拒绝（收紧而非换方案）。同理，强制 TOTP 的开关是用户要用的东西，不是漏洞。

### 第二轮的教训：我自己的修复里也有同类残留

再复核在**我的修复**里又找出 11 条，其中 2 条（F11 / F12）与修复前是**同一类**缺陷：
`RestoreWizard.vue` 用了未 import 的 `<PathText>`（`vue-tsc` 查不出未解析组件）；
以及"没有出口的房间"我只堵了一半判据（`canExecute` 有三条，我只验了两条）。

> **教训**：修这类缺陷时要把**所有判据逐条走一遍**，而不是只修触发当前症状的那一条。
> 另外 `MaxSelectedPaths = 12000` 那个常数我也算错了（链长上界是 10001 而不是"数百"，
> 12000×2+10001 仍然越界）——**常数要么算准，要么改成动态算，不要写一个"看起来有余量"的值。**
