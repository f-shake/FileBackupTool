## 判据：本角度要守的不变量

这些不是泛泛的"代码质量"，是**错了不会报错、只会静默产生错误数据**的那一类性质。
复核时逐条问"有没有哪条路径能违反它"。

| # | 不变量 | 违反的后果 | 出处 |
|---|---|---|---|
| E1 | **blob 名 == 内容哈希**。任何写 blob 的路径，命名用的哈希必须是**写入那份内容**算出来的 | blob 池被静默污染，且被后续快照反复复用；全部完整性校验失效 | [09 B4](../plans/09-实现期修订.md) |
| E2 | 快照链区间比较一律用 `SnapshotId`，**不用** `BeginTime` | 同刻创建的快照被静默排除出链 → "墓碑写了但镜像没变" | [09 B1](../plans/09-实现期修订.md) |
| E3 | 镜像 = 最新 Full + 其后增量按 `Created→加 / Modified→换 / Deleted→删` 重放；**软删除记录不参与镜像** | 还原出已被删掉的文件 | `03 §1` |
| E4 | 镜像规模数学：`imageCount = prev + created − deleted`；`imageBytes = prev + createdBytes + modifiedDelta − deletedBytes`。全量与增量**同一个公式** | 抢救清单头部规模失真 | [09 A3](../plans/09-实现期修订.md) |
| E5 | **只要还有任何记录（含软删除）引用某个 blob，它就不可回收** | 可回溯的语义被破坏（删快照后空间立刻释放） | 决策 #12、`02 §5.1` |
| E6 | 还原选靶：每个路径取链上**最新非 Deleted** 的那条记录 | 还原错版本 | `04 §1` |
| E7 | 清单片名对真实段名是**单射转义**（`%`→`%25`，`_`→`%5F`），字面 `_root` 不可能被真实段名占用 | 两个来源写进同一文件 → 静默丢条目 | [09 G2](../plans/09-实现期修订.md) |
| E8 | 落库、写清单、回收这三步一律用 `CancellationToken.None` | 快照永远停在 `InProgress`，或"说 Completed 却抛取消" | [09 B6](../plans/09-实现期修订.md) |
| E9 | `RelativePath` 保原始大小写（只用于还原重建路径），`RelativePathKey` 归一化（所有比对/索引/唯一性） | 在 NAS/Linux 上还原出的文件名全变小写 = 批量改名 | [09 A1](../plans/09-实现期修订.md) |
| E10 | `Guid` **交给驱动绑定**，不手写 `ToString()` 形式 | 手写 SQL 静默匹配不到 → TEMP 镜像表为空 → 增量退化成"全是新增" | [09 F1](../plans/09-实现期修订.md) |
| E11 | 部分写入保护：`(Length, LastWriteTimeUtc)` 稳定满 `SettleWindowSeconds` 才放行 | 备份到写了一半的文件 | `03 §3.4` |
| E12 | 去重的 `Length` 预筛：只有**池中不存在同长度记录**时才可"边拷边算"下结论 | 少算一次哈希却漏判重复 → 无谓写放大（10GB 级） | `03 §3.3` |

### 值得单独说的两条

**E1 为什么排在最前。** 它不是"边界情况"，而是**常规路径**：任务开着监控 → 第一个快照之前正好有文件改动
→ `DecideNextType` 返回 Full（还没有任何 Full）→ 第一个快照就是一个只覆盖变更目录的"全量"。
而它会成为后续所有增量的基准，还会让抢救清单被重写成只剩那棵子树。属静默数据损坏。

**E7 上两份报告结论相反，我实测定的案。** 一个 Agent 说 EF 会把 `Contains` 参数化成 `json_each`、
参数不随链长膨胀；另一个说不参数化、会撞 32766。我用 `ToQueryString()` 量了：

```
10 个元素   →   899 字符
5000 个元素 → 307045 字符      （SQL 文本随元素数线性增长）
Assert.Contains("json_each", sql)  →  失败
```

**会内联**。所以第二个 Agent 是对的，文件历史端点确实会在快照数超过 32766 时以
`too many SQL variables` **直接失败**（不是变慢）。修完之后我把这个事实写成了常驻测试，
而不是留在"我记得 EF 8 之后改过"这类记忆里。

## 第二轮：再复核后补上的两条

我再复核时把修复清单回传给同一个子 Agent，它核对后提出两条**我漏掉的可达路径**，都属实、都已修。
这两条有一个共同点：**都是"参数会被内联进 SQL"这个事实的下游**，而 E7 那次实测才让我真正看清它。

### E16【已修】显式请求增量会绕过"超限转全量"，把链推过 SQLite 参数上限

`DecideNextTypeAsync`（那个"增量数超过 `MaxAutoIncrementBackupCount` 就转全量"的决策）
**只在调用方没有显式指定类型时才被咨询**：

```csharp
SnapshotType type = requestedType ?? await _chains.DecideNextTypeAsync(task, ct);
```

而 `POST /api/tasks/{id}/backup` 可以带 `{"type":"Increment"}`。于是连续请求增量能把链一路推过
32766 —— 然后 `PreviousMirrorTable` 的 `IN (chainIds)` 参数过多，**该任务的增量备份与还原开始显式失败**，
直到有人手动跑一次全量把链重置。（响亮的失败，不是静默损坏，但它是一个"用户能自己把功能按死"的口子。）

**修法**：`BackupEngine` 里加 `MaxIncrementChainLength = 20000`，超了就在同一条退化路径上转全量 ——
取舍与文件里那句"宁可多写一份数据，也不能写出一条 replay 不通的坏链"完全一致。
**注意**：这条守卫不依赖 `DecideNextTypeAsync` 被咨询过，所以也顺带守住了
`GetTotalsAsync` / `EnumerateChainPathKeysAsync` / `SourceReadCount` 那几处同样未分块的 `Contains`
（它们的入参都是"链"或"级联删除集合"，都受这个上界约束）。

### E17【已修】脏目录数没有**绝对**上限，只靠占比

`PreviousMirrorTable` 的前缀 OR 列表按 **2 个参数/前缀**内联，而脏目录数只受
`LocalScanDegradeRatio`（占比超过 30% 才退化全量）约束。源树目录数上万时，**30% 以内就能过万** ——
占比判据拦不住，而约 16384 个脏目录会让**增量备份以 SQLite 报错中止**。

这比 E13（还原侧）严重：还原失败用户还能改范围，**备份失败是"核心功能在目标规模上停止工作"**。

**修法**：`NormalizeDirtyScopes` 里加 `MaxDirtyScopeCount = 8000`，超过就退化为全量扫描。
8000 的依据是算出来的：`1 + 链长 + 2N`，链长即使按被夹住的上界 10001 算，也只有 26002 < 32766。
退化在语义上是**免费的**（局部扫描只是省读，全量总是更完整）。
