### F1：为什么它能一直藏在"编译通过"后面

三条线索单看都不像 bug：`canExecute` 的写法（"没有计划就不能执行"）是对的；
按钮的 `:disabled` 也合理；`next()` 在 `step === 2` 时调 `runPlan()` 也合理。
**问题在它们的组合**：进入 step 2 的唯一入口就是那个按钮，而按钮的启用条件依赖
只有该按钮能触发的动作。这是一个"没有出口的房间"，而类型系统看不到这种结构。

修法选了"自动预演"而不是"把按钮改成可点"：按钮文案本来就写着"重新预演并继续"，
语义更像"重跑一次"；首次进入这一步应当**自动出结果**。另外补了一条"这个范围内没有可还原的文件"
的提示——因为当 `writeCount === 0 && skipCount === 0`（全部不可恢复）时按钮**仍然**是禁用的，
没有说明就又是一块没有出口的面板。

### F5：判决依据来自后端，而不是文档

两个组件对**同一个** `log.appended` 事件做了**相反**的追加（一个前插、一个后插+滚到底），
必有一错。子 Agent 判 PLAUSIBLE，理由是 06/07 文档没把 `/api/logs` 的排序写死。
我去后端找到了权威依据：`LogsController` 是

```csharp
.OrderByDescending(l => l.Time).ThenByDescending(l => l.Id)
```

**最新在前**。所以 `TaskDetailView` 的前插正确、`TaskLogsPanel` 错。顺带说明：
后端还专门用 `Id` 作次序键，因为一次备份会写很多条同毫秒的日志，否则翻页会重复或漏行——
`TaskLogsPanel` 的实时插入也应保持这个方向。

**这条的教训**：当两个地方对同一份数据的顺序做了相反假设时，**不要看哪边的代码更"顺眼"，
去找到数据的产生方**。前端这边的"约定"没有任何一处写在文档或类型里。

### F7：为什么"只补 `jobTask`"就够了

缺口是**身份映射**（哪个 `jobId` 属于哪个 `taskId`），不是进度本身：
`liveProgress` 要的是 `jobTask[jobId]` → `progressByJob[jobId]`，后者由 `backup.progress`
持续填充（250ms 节流）。所以只要在重连/REST 兜底时把 `running` / `queued` 的
`jobId → taskId` 补上，下一个进度事件（不到 250ms）就会把进度条点亮。
刻意不补 `progressByJob`：那需要把 `JobProgress` 映射成 `BackupProgressEvent`（两个不同形状），
而收益只是省掉一个四分之一秒。

用的是 `monitoringApi.listJobs()` —— 它原来正是 F10 清单里的一条死代码，现在有了真实用途。

## 第二轮：复核者在我的修复里找出 4 处残留，其中 2 处是**同一类新洞**

再复核时子 Agent 给出 6 条 FIXED、4 条 PARTIAL，并**新发现一条比所有残留都严重的缺陷**。
这一册是六册里"修完还得再修"最多的，原因很集中：**前端没有运行期反馈**，
所以"改对了方向但没改到底"不会被任何东西拦住。

### F11【已修·本轮最严重】`RestoreWizard.vue` 用了未 import 的组件

`<PathText>` 在模板里用了，但 `import` 区没有它，全仓库也没有 `app.component(...)` 全局注册
（`main.ts` 只 `use(Pinia/router/ElementPlus)`，`vite.config.ts` 没有自动导入插件）。
对照表很干净：其余 8 个用到它的组件全都显式 import 了，只有这一个漏了。

**为什么 `vue-tsc` 查不到**：模板里的未知组件不产生类型错误（它可能来自全局注册），
所以生产构建里**静默渲染成一个空的自定义元素**——还原执行时"当前正在还原的文件"那一行什么都不显示。

**这正是"构建通过 ≠ 能跑"的教科书案例**，也是本册存在的理由。

### F12【已修】我自己补的那个说明没堵住死路，因为 `canExecute` 的第二条判据不可达

我上一轮补了"没有可还原文件"的提示，但漏了另一半：

- `canExecute` 第二条：`if (blockedItems.length > 0 && !acknowledgedBlocked.value) return false`
- 按钮：`:disabled="step === 2 && !canExecute"`
- 而那个勾选框 `v-model="acknowledgedBlocked"` 只在**第 3 步**渲染

于是有"不可还原"文件的快照（**正是 04 §1.6 要求支持的场景**）在第 2 步会看到**灰色且点不亮的按钮**，
却找不到任何能勾的东西——**与修复前那个死路是同一类**。我只堵了 `writeCount`/`skipCount` 那一半。

**修法**：把勾选框同时渲染在第 2 步的不可还原清单下方（步骤互斥，不会同时出现两个）。

> **这条的教训值得单独记**：修"没有出口的房间"这类缺陷时，**要把所有判据逐条走一遍**，
> 而不是只修触发当前症状的那一条。`canExecute` 有三条判据，我只验了其中两条。

### F13【已修】输入变了却沿用旧计划

`plan` 只在打开向导时被清空，所以"上一步改范围/改还原根 → 下一步"会**沿用旧计划**：
面板上的"将写入 N 个文件"与清单里的目标路径全是旧输入的，而 `buildRequest()` 读的已经是新值。

**后端不会兜住**：`RestoreController` 明确写着"接受 `planToken` 字段并原样忽略"（恒返回 `null`）。
引擎执行时逐条重判冲突，所以不会误覆盖文件，但**用户确认过的落点是错的**——这比没有预演更糟。

**修法**：`watch([scope, targetRoot, targetSubPath], () => { plan.value = null })`——
输入一变计划作废，上面那个自动预演的 watcher 自然会重新触发。

### F14【已修】取消后被渲染成绿色的"还原完成"

`Aborted` 与 `Completed` 混在一个分支里，本地拼出的结果没有"已取消"这一维，于是：

- 终态卡显示绿色对勾 + "还原完成"——用户刚点的就是取消；
- **排队中取消**更荒谬：服务端写的 `Error = "已取消（尚未开始）"` 被"有 error 就算一个失败文件"
  塞进 `failures`，于是同屏出现**绿色"还原完成" + 红色"1 个文件还原失败"** + 一行 `relativePath` 为空的表格。

**修法**：加 `canceled` 状态（终态卡换成 info 图标 + "还原已取消" + 说明），
并让 `job.error` **只在真失败时**才当失败条目——取消原因是状态说明，不是文件失败。

### 子 Agent 回答"自动预演 vs 把按钮改成可点"：认可自动预演

它的理由比"文案"更硬，我接受：

> 第 3 步的产出是**只读结果**，进入即计算才符合两段式的语义 —— `loadRoots()` 对第 1 步就是这么做的。
> 让用户先到一个空步骤、再点第二个按钮才有东西可看，等于把"预演"变成了一个动作而不是一个状态。

它补的前提也对：**自动预演必须跟着输入走**，不能只判 `!plan.value`——这就是 F13。
