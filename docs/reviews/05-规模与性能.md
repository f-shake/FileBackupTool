# 05 · 规模与性能

> 复核角度：物化、N+1、索引覆盖、SQLite 细节、字符串分配、启动路径、前端分页。
> 总索引见 [README](README.md)。

## 复核范围

后端全量 + `web/src`

## 前提：设计时钉死的规模目标

这是本角度的**唯一尺度**。脱离它谈性能没有意义。

| 目标 | 含义 |
|---|---|
| **百万文件级** | 不是"几千个文件的小目录"；任何 O(文件数) 的内存结构都不合格 |
| 内存 **O(1)**（与文件数无关） | 全程流式；不许 replay 整条链、不许把清单全读进内存 |
| 源盘与目标盘都是**机械盘** | 顺序 IO 为王；随机寻道是主要成本 |
| 单用户 | 并发压力不是问题，"一次操作的成本"才是 |

## 判据

| # | 要问的问题 | 违反的后果 |
|---|---|---|
| P1 | 有没有哪条路径把**整条链**或**整份文件列表**读进内存？ | 百万文件下 OOM；这正是 `PreviousMirrorTable` 用 TEMP 表存在的原因 |
| P2 | 镜像物化是否走 `(RelativePathKey ASC, SnapshotId DESC)` + 索引同向？ | 索引方向不一致 → SQLite 为百万行做外部排序（写临时文件、慢几个数量级） |
| P3 | 有没有 N+1 查询（循环里查库 / 逐条 `SaveChanges`）？ | 每次一个往返；10 万次 = 分钟级 |
| P4 | 批处理是否 `TakeBatchAsync`（SELECT + DELETE 一次搞定）？ | 分两次做 = 两倍往返 + 竞态 |
| P5 | 每文件路径上有多少**分配**（字符串拼接、LINQ、正则、`ToUpper`）？ | 百万次 × 每次几 KB = GC 压力把 IO 时间淹掉 |
| P6 | `AsNoTracking` 是否覆盖只读查询？ | 变更跟踪器持有全部实体 → 内存随查询增长 |
| P7 | SQLite 参数：`WAL` / `synchronous=NORMAL` / `busy_timeout` / `foreign_keys=ON` 是否都生效？ | 回滚日志模式下每次提交 fsync；FK 默认不强制 |
| P8 | 启动路径的开销：无条件全量扫描在百万文件下要多久？会不会阻塞宿主启动？ | 公网服务重启后长时间不可用 |
| P9 | `SaveChanges` 的批大小是否可调且合理？ | 太小 = 事务开销主导；太大 = 单次事务过长 |
| P10 | 前端列表是否分页？有没有一次拉全量？ | 快照/文件列表可能上万条 |
| P11 | 有没有可以**避免的读**（例如为了算哈希而多读一遍盘）？ | 机械盘上读一遍就是全部成本 |

| P3 | `ListChangesAsync` 无可支撑索引（变更面板一次请求 = 3 次全量 COUNT + 无索引排序；Full 快照 1M 条时每个 count 都走完 1M 索引项） | ⚠️ | PLAUSIBLE | **未修**，见 J5 #4（需加组合索引 + 迁移） |

| P5 | 单文件失败 = **一次独立事务**的日志写入（`LogStore.WriteManyAsync` 已存在但没用） | ⚠️ | ✅ 属实 | **未修**，见 J5 #6 |
| P6 | 目录树接口用 `children.Any(...)` 对已收下的同级子目录线性查重（O(D×C)） | 🔧 | PLAUSIBLE | **未修**，见 J5 #9（`childCounts` 字典本来是现成的） |

### 这一册里最重要的一件事：**它有一处结论是错的，而错的那处恰好最危险**

P1 的子 Agent 在"未发现问题"一节里写道：

> `EF 对 chainSnapshotIds.Contains(...)` 走参数化集合（json_each），参数不随链长膨胀。

并据此把**文件历史会撞 32766 参数上限**这条判为不存在。另一个角度（引擎/数据）的判断正好相反。
**两份报告的结论直接冲突，我实测定案**（`ToQueryString()`）：

```
10 个元素   →   899 字符
5000 个元素 → 307045 字符        SQL 文本随元素数线性增长，json_each 断言失败
```

**EF 会逐元素内联。** 所以这条隐患是真的：`MirrorQueryService.GetFileHistoryAsync` 传的是
"该任务**全部**已完成快照的 id"（随快照数单调增长），而 `FileRecordStore.GetFileHistoryAsync`
当时**没有**分块（同文件其它方法都分了）→ 长期开着监控的任务迟早以 `too many SQL variables`
**直接失败**。已修 + 回归测试。

**教训**：这一册的价值取决于它对 provider 行为的断言准不准，而"我记得 EF 8 之后改成参数化了"
这种记忆是不可靠的。凡是"某库会不会把 X 翻译成 Y"的结论，**都应当能指向一次实测**——
所以我把这次的实测写成了常驻测试（`SqlParameterizationTests`），而不是留在文档里。

### 子 Agent 逐行核对后**没**发现问题的点（供交叉核对）

它列了一批，我抽验后认可：

- `Length` 预筛是**按批**查的（`GetKnownLengthsAsync` 以 800 分块 + `Distinct()`），不是按文件；
  `GetReferencedBlobsAsync` / `GetRecordsByPathKeysAsync` / `GetBlobRepresentativesAsync` 同样分块。
- 记录写入是每 2000 条一次 `SaveChangesAsync` + `ChangeTracker.Clear()`，没有在 EF 里攒整快照。
- `PreviousMirrorTable` 的建表 + 灌数据在同一事务内；`ORDER BY RelativePathKey ASC, SnapshotId DESC`
  与 `(TaskId, RelativePathKey, SnapshotId DESC)` 索引方向一致；TEMP 表在 `DisposeAsync` 里 DROP。
- **启动路径无全表扫描**：`MigrateAsync` 无待应用迁移时只读历史表，`SessionRegistry.LoadAsync` 读单行
  `AppSetting`，`StartupSelfHealService` 只做按任务的目录存在性探测与 `InProgress` 归位，
  且不阻塞 `app.RunAsync()`。
- 任务列表/详情是聚合 SQL（无 N+1）；前端全部走服务端分页，未对百万级数据做客户端排序/过滤。
- `GarbageCollector.VerifyAsync` 的 `pool`（1M blob ≈ 90 MB）在代码注释里已被显式接受，
  且它是手工触发的完整校验。

## 第二轮：P1 的守法和上限值都写错了，而且备份路径根本没被守住

再复核时子 Agent 指出两处，都属实、都已修。**P1 是这一册唯一需要动代码的条目，
而我第一次修得不对**——值得完整记下来。

### P1a【已修】`MaxSelectedPaths = 12000` 这个常数在算术上不成立

我原来写 `12000`，注释理由是"链长(≤ 数百)"。**那是假设，不是约束**：
链长被强制夹住的上界其实是 **10001**（`MaxAutoIncrementBackupCount` 在
`TasksController` 里被夹到 ≤ 10000）。于是：

```
1 + 10001 + 2×12000 = 34002  >  32766      ← 仍然越界
```

**修法**：**按实际链长动态算预算**，不再写常数，而且检查移到链解析**之后**
（原来在之前，那时还不知道链有多长）：

```csharp
const int SqliteParameterLimit = 32766;
int pathBudget = (SqliteParameterLimit - chain.Count - 2) / 2;
```

这样与链长彻底解耦，也不依赖任何关于"链长只有几百"的假设。

### P1b【已修】备份路径完全没被守住，而它比还原更该守

`PreviousMirrorTable.BuildAsync` 是 public，而它的**另一个调用方**
（`BackupEngine.RunIncrementAsync` 的 `dirtyScopes`）不受任何上限约束：
`NormalizeDirtyScopes` 只有祖先压缩、没有计数上限，脏目录数只受
`LocalScanDegradeRatio`（占比 30% 才退化）约束 —— 源树目录数上万时，**30% 以内就能过万**。

量级上这比还原那条严重：还原失败用户还能改范围，**备份失败是"核心功能在目标规模上停止工作"**，
而且中止的是快照。

**修法**：加 `MaxDirtyScopeCount = 8000`（算法：`1 + 10001 + 16000 = 26002 < 32766`），
超过就退化为全量扫描。**退化是免费的**：局部扫描只是省读，全量总是更完整。

### 子 Agent 对"要不要现在改成 TEMP 表联查"的回答：**不要**

它的理由我认可，也补一句我自己的判断：

> 前缀 OR 列表的每条都是一次索引 seek（`=` 与 `LIKE key\` 前缀区间），与
> `ORDER BY RelativePathKey` 的索引同向关系正是本册 P2 判据的核心；改成 TEMP 表联查会引入
> 第二张 TEMP 表的写入 + 大概率多一次排序。**参数上限问题的正确修法是"不让它越界"，
> 不是"换 SQL 形状"。** 只有把"一次还原任意多个选中文件"做成一级功能时才该上 TEMP 表联查，
> 并且要**实测**它与现方案的 `ORDER BY` 计划差异后再决定。

### 它给的优先级排序（我认可，并已写进 09 J5）

它补了一条我没列的、并且把它排在最高：

| 优先级 | 条目 | 理由 |
|---|---|---|
| **P0** | 备份脏目录前缀无上限 → **增量备份硬失败** | 唯一一条会让核心功能在目标规模上**直接失败**的；修法最便宜（一个常量 + 退化，无新 SQL、无迁移）。**已在本轮修掉（P1b）** |
| 1 | **P2** O(N) 内存集合 | 唯一剩下的 O(N) 结构，是**冻结前提的违约**（不是调优）；量级**确定发生**、不依赖任何 planner 行为 |
| 2 | **P3** 缺组合索引 | 常规 UI 动作的可感延迟，落在"索引是生死线"的前提上；**但建议与下一次必定要做的迁移合并**，别为它单独发一次迁移 |
| 3 | **P5** 每失败一次事务 | 只在失败路径触发且被阈值夹住上界；不会在正常运行的库上表现出来 → 可放到 v1.1 |
| 4 | **P6** O(D×C) 查重 | 一行改动，但不改也能用 |
| — | **P4** 搜索整链物化 | **不列为待修项**，改为扩写 `08 §5.2`（与已接受的"深快照链浏览"悬崖同根因）。唯一值得补的一句：`FilesController` 拒绝 `path` 参数意味着"搜索必然整任务扫描"是**接口契约层面**的事实，不只是某个调用点的实现细节 |
